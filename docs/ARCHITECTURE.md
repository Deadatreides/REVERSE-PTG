# Обратный PTG — архитектура MVP

Рабочее имя пакета — `rptg`, окончательное название за автором. **Версия 0.3 от 27.09.2026.**

* Логика работы — в [LOGIC.md](LOGIC.md).
* Факты и допущения, на которых стоят решения, — в [BASIS.md](BASIS.md).
* Основа: [REVERSE-PTG-SPEC.md](../../for%20codex%20(1.1)%20—%20копия/REVERSE-PTG-SPEC.md) (история) и
  [REVERSE-PTG-VERIFICATION.md](../../for%20codex%20(1.1)%20—%20копия/REVERSE-PTG-VERIFICATION.md).

**Что изменилось против 0.2 после сверки с базой PTG:**

* **«Сначала целиком».** Узел раскладывается по необходимости, а не потому, что выглядит сложным:
  декомпозиция сама по себе качества не добавляет (F28, LIFE-9, experiment14).
* **Маршрутизация — по классу работы и измеренной таблице компетенций** (experiment14: +0,38).
  Формула по карточке — только холодный старт.
* **У каждой проверки — контрольные случаи** (F45, arch1).
* **Приёмка названа точно:** «соответствует карточкам», а против замысла проверяют только примеры
  пользователя (SEAM_MODEL §2.2).
* **Починка — без прежнего ответа целиком.** Нарушение формы идёт отдельным путём; на ступени одна
  починка содержания (experiment10–12).
* **Добавлен §12 — как проверяется сам продукт.** Против плоского базиса, при равном бюджете, в
  целевом режиме.

## 0. Что это и где границы MVP {#purpose}

**Назначение.** Программа строит другую программу по графу. Пользователь описывает замысел и даёт
приёмочные примеры. Дальше работают три роли — каждую может играть любая модель:

* **архитектор** строит центральный узел с его рёбрами и **общую карту сети** — текст с эскизом
  всех ветвей;
* **конструкторы** рекурсивно достраивают сеть: составной узел раскладывается на дочерние узлы и
  рёбра между ними;
* **исполнители** пишут код финальных узлов — листьев. Рёбра они не трогают и не видят.

**По умолчанию узел финальный.** Составным он становится, только когда это необходимо:

* ему есть кого вызывать;
* у него много операций;
* он не помещается в функции допустимого размера;
* его функция не далась всей лестнице исполнителей.

**Какая модель делает какой узел**, решает маршрутизация:

* ручное назначение;
* **измеренная таблица компетенций** — успех каждой модели по классам работы на одинаковых
  эталонных задачах;
* пока таблицы нет — прикидка по карточке.

Например: Opus или Астра — архитектор, Gemini или Grok — конструкторы средних уровней, мини-модель
через OpenRouter или локальная модель — исполнитель там, где таблица показала, что она справляется.

Всё, что пишут модели, принимает только скрипт — детерминированными проверками по карточкам уровня
выше.

**Главное устройство.** Модели пишут только карточки, схемы потоков и код листьев. Соединительный
код — как значения текут от узла к узлу — **генерирует сам скрипт** из схем потоков. Поэтому граф в
коде не может разойтись с графом в карточках. Подробно — [LOGIC.md §2](LOGIC.md#flow-model).

**В MVP входит:**

| что | как |
|---|---|
| целевой язык | Python ≥ 3.10 |
| тип целевых программ | программы-конвейеры: утилиты, обработка данных, расчёты, простые боты. Состояние передаётся явными записями, ввод-вывод — в объявленных листьях |
| граф | дерево разложения любой глубины (по умолчанию не глубже 8) + рёбра потоков внутри каждого составного узла + разрешённые связи между поддеревьями |
| роли | архитектор, конструктор, исполнитель; ручные назначения на узел, поддерево или уровень |
| маршрутизация | вид узла по правилу «сначала целиком»; класс работы по карточке; оператор — по ручному назначению, таблице компетенций или прикидке; журнал исходов |
| калибровка | `rptg models calibrate`: эталонный набор функций по пяти родам, одинаковый для всех операторов, подбор и проверка на разных половинах |
| модели | любые: Anthropic, OpenAI, Google, xAI, OpenRouter, любой OpenAI-совместимый сервер (в т. ч. локальный), GGUF через llama.cpp в процессе; вперемешку в одном проекте |
| проверки до кода | П1 форма, П2 структура, П3 совместимость данных, П4 совместимость условий, П7 примеры — на каждом разложении любой глубины |
| проверки после кода | Э1 статика, Э2 условия в исполнении, Э3 тесты на свойства — на функциях листьев; Э6 сборка — на каждом составном узле снизу вверх |
| доверие к проверкам | у каждой проверки — контрольные случаи с известным ответом; не прошедшая их проверка HARD-доказательств не выдаёт |
| окно | карта сети, схемы потоков, карточки, назначения, таблица компетенций, доказательства и контрпримеры, примеры пользователя на любом узле, утверждение карты, журнал, расходы |
| исполнение | последовательное, с возобновлением с места остановки |

**Вне MVP:**

* П5 — доказательство уточнения: считается, но не блокирует;
* П6 — протоколы событий, П8 — прослеживаемость;
* Э4 — символьная проверка, Э5 — мутации, Э7 — анализ влияния;
* калибровка разложений — нужен набор эталонных замыслов (v0.1);
* подбор весов прикидки по журналу — только если калибровка покажет, что прикидка вообще связана с
  успехом;
* JS/TS, связанные репозитории, `.exe`, ключ Pro, параллельные исполнители;
* **рой локальных мини-моделей по схеме Кана.** Приоритет низкий: сверх лучшей одиночной модели рой
  добавлял +0,05…+0,08 и ни разу значимо (K1, LB2, SWE1), а маршрут по роду работы — +0,38
  (experiment14).

## 1. Главные решения {#decisions}

| № | решение | почему |
|---|---|---|
| **D1** | **Скрипт решает, модели пишут.** Приём — только HARD-проверки. Отзыв модели — SOFT, может лишь поднять флажок | F9: сгенерированный моделью проверяльщик отверг правильный эталон в 129 случаях из 168; F11, F12, F14. Замеры на моделях 0,4–1,7B — берётся направление, а не число |
| **D2** | **Всё, что пишет модель, — данные в строгой схеме.** Карточки и схемы потоков — JSON по JSON Schema; код — ровно один блок с одной функцией. Файлы целевого проекта пишет только скрипт | модель, пишущая файлы сама, выходит за карточку |
| **D3** | **Соединительный код генерирует скрипт** из схем потоков; модели пишут только листья | граф в коде совпадает с графом в карточках по построению. SWE1: без принудительной сверки швов разрезанная задача дала выдуманные вызовы в 0,50 патча против 0,05 у одного исполнителя |
| **D4** | **Условия — на формальном языке CL**, одна запись → Z3, проверка Python, генератор Hypothesis | без формы нечего доказывать |
| **D5** | **Разложение рекурсивное, любой глубины, но только по необходимости.** Каждый ребёнок строго меньше родителя, детей немного | F28, LIFE-9, experiment14 G2 = 0: декомпозиция не повышает качество; она окупается за пределом окна (SWE1) и для локализации ремонта (F29, F42). E6/G1: выигрыш — только когда каждая часть строго легче целого |
| **D6** | **Роли, а не уровни.** Архитектор — корень и карта; конструктор — разложение одного составного узла; исполнитель — код одной функции листа | роль определяется задачей, а не местом в иерархии |
| **D7** | **Маршрут по классу работы и измеренной таблице компетенций + ручное назначение.** Прикидка по карточке — только пока таблицы нет | experiment14: маршрут по роду шага решил 0,43 задач против 0,05 у лучшей одиночной модели. Сравнение — только при равной выборке, подбор и проверка на разных половинах |
| **D8** | **Любые поставщики вперемешку** за одним интерфейсом. Строгость формата обеспечивает скрипт, а не поставщик | не привязывать людей к одной платформе |
| **D9** | **Минимальный контекст задачи:** своя карточка + интерфейсы соседей + отчёт о нарушениях; стабильное — первым, для кэша. При починке прежний ответ целиком не показывается | CONTEXT_MODEL §4, F35: соседние ветви не нужны; F1: ошибка привязана к паре (модель, задача) |
| **D10** | **Приёмка по доказательствам на текущем хэше.** «Принят» = соответствует карточкам; против замысла проверяют примеры пользователя | SEAM_MODEL §2.2: тесты, написанные моделью, — HARD к вопросу «соответствует ли», SOFT к вопросу «корректно ли» |
| **D11** | **Владение:** интерфейс узла меняет только тот, кто его создал, — разложивший родителя. Разложение узла меняет только тот, кому оно поручено. Правка — новая ревизия, зависимое устаревает | исполнитель и конструктор ниже не подгоняют задачу под ответ |
| **D12** | **Воспроизводимость:** зерно, тайм-ауты, версии инструментов — в доказательствах; сырой ответ и `finish_reason` — в попытках | тот же вход → тот же вердикт; F45: дефекты находятся пересчётом по сырью |
| **D13** | **Чужой код — только в песочнице:** отдельный процесс, временная папка, тайм-аут, очищенное окружение; опасное запрещено статически, если карточка не разрешила | код пишет модель — он недоверенный |
| **D14** | **Всё состояние — в `.rptg/`**, журнал только дописывается | остановка и продолжение с той же точки |
| **D15** | **Проверки проверяются.** У каждой — контрольные случаи; извлечение ответа — внутри проверки | F45; arch1: 59,6 % первичных FAIL оказались ложными из-за извлечения вне проверки |
| **D16** | **Профиль ведётся на оператора** — модель + настройки + версия подсказки + роль, — а не на модель | F3, F4, F25: влияние настроек и формулировки разнонаправленно по моделям |
| **D17** | **Политика элемента — генотип на языке комплексов arch2** (CALL, CHECK, SEQ, PAR, SWITCH, BUDGET, STOP), а не зашитые правила. Циклов нет. Умолчание выведено из измеренного, альтернативы выбираются повтором по журналу | язык в проекте уже измерен и реализован (arch2, 152 контрольных случая); без цикла верхняя стоимость считается статически. LOGIC §7.3, BASIS §1.7 |
| **D18** | **Механика переносится из arch0–arch2 вместе с контрольными случаями**, а не пишется заново | реестр проверок, STALE, исполнитель политики, повтор без токенов уже проверены: arch1 — 91 случай, arch2 — 152. design/map.md §9 |

## 2. Состав: ядро и модули {#modules}

```
слой 6   cli
слой 5   core (конвейер)      bench (калибровка, замеры)      gui
слой 4   verify
слой 3   route      tasks      codegen
слой 2   cond
слой 1   schemas    store      journal
слой 0   model      sandbox    llm
```

Модуль зависит только от модулей в слоях ниже. Кто от кого именно — в таблице.

| модуль | ответственность | зависит от |
|---|---|---|
| **core** (ядро) | конвейер: очередь разложения сверху вниз, очередь постройки снизу вверх; цикл «написать → проверить → принять / повторить форму / чинить / поднять»; подозрение на карточку; устаревание; ворота утверждения; остановки; бюджет; возобновление | model, store, journal, route, tasks, verify, codegen, llm |
| **bench** | калибровка операторов на эталонных наборах при равной выборке, подбор и проверка на разных половинах, гейт G0, таблица компетенций; замеры продукта против плоского базиса (§12) | model, store, journal, tasks, verify, llm |
| **model** | типы данных: проект, узел, операция, пример, схема потока, тип, карточка, разложение, ревизия, оператор, роль, класс работы, назначение, задача, попытка, доказательство, исход | — |
| **store** | раскладка `.rptg/`, атомарная запись, ревизии, хэши | model |
| **journal** | журнал событий: восстановление, лента для окна, журнал исходов, выгрузка в PTG-MEM (v0.1) | model |
| **route** | вид узла («сначала целиком»); класс работы по карточке; выбор оператора — ручное назначение, таблица компетенций, прикидка; лестницы; адаптация (выключена по умолчанию) | model, cond, schemas |
| **cond** | язык условий CL: разбор, типы, компиляция в Z3 / Python / Hypothesis; размер выражения, кванторы и нелинейность для рода работы и прикидки | model, schemas |
| **schemas** | реестр типов (подмножество JSON Schema), подсхемы (jsonsubschema), классы данных Python, размер типа | model |
| **verify** | проверки с общим интерфейсом доказательств: `form` П1, `graph` П2, `data` П3, `logic` П4 П7 (+П5 без блокировки), `code` Э1–Э3, `assembly` Э6; у каждой — контрольные случаи и признак доверия | model, cond, schemas, codegen, sandbox |
| **codegen** | целевой проект: типы, листья, соединительный код из схем на каждом составном узле, обёртки условий, тесты, заглушки | model, cond, schemas |
| **sandbox** | запуск кода и тестов в отдельном процессе | — |
| **tasks** | задачи для ролей: подсказки с версиями, альтернативные формулировки для повтора формы, минимальный контекст, отчёт о нарушениях, строгий разбор ответа под способ структурного вывода оператора | model, cond, schemas |
| **llm** | поставщики за одним интерфейсом, профили операторов, учёт токенов, стоимости и `finish_reason`, повторы на сетевых сбоях | — |
| **gui** | карта сети, схемы, карточки, назначения, таблица компетенций, доказательства, примеры пользователя, утверждение, журнал, расходы | store, journal; команды в core — через очередь |
| **cli** | команды пользователя | core, bench, store, gui |

## 3. Данные на диске {#storage}

```
<целевой проект>/
  .rptg/
    project.yaml              замысел, операторы, роли, лестницы, назначения, пределы, бюджет
    examples.yaml             примеры пользователя — эталон замысла; на корне обязательны, на любом узле по желанию
    map.md                    текст архитектуры от архитектора, разделы {#id}
    types/<Type>.json         именованные типы
    cards/<node>.json         карточки узлов любой глубины
    designs/<node>.json       разложения составных узлов: дети, типы, схемы потоков
    revisions/<node>/<n>.json версии карточек и разложений + причина; ничего не удаляется
    code/<node>/<op>.py       принятый код функции листа — только функция
    evidence/<subject>.jsonl  доказательства
    attempts/<task>/<n>.json  попытки: оператор, запрос как ушёл (ProviderRequest, ключей в нём нет), сырой ответ до разбора, finish_reason, расход, вердикт
    outcomes.jsonl            исход каждой задачи: оператор, класс, прикидка, ступени, попытки, итог, цена, «разведка»
    approvals.jsonl           утверждения пользователя
    journal.jsonl             журнал событий — источник истины
  src/<package>/              собранная программа — пишет только codegen
  tests/                      сгенерированные тесты

~/.rptg/
  competence.json             таблица компетенций: оператор × класс → успех на подборе и проверке, выборка, цена на успех
  calibration/<run>/          прогоны калибровки с сырьём
  reference/                  эталонные наборы: карточки функций со скрытыми тестами
```

Таблица компетенций общая для всех проектов пользователя: она описывает операторов, а не проект.

**Как сделано в оболочке** (`rptg_host`, 04.10.2026) — проще целевой раскладки выше:

```
<проект>/
  project.yaml        настройки (Config): операторы, роли, лестницы, назначения, пределы, маршрутизация
  .rptg/state.json    состояние ядра (State) целиком — пишется атомарно (временный файл и замена)
  .rptg/journal.jsonl события и записи журнала переходов со временем оболочки — только дописывается
  .rptg/calls/<n>.json вызов модели: задача, запрос как ушёл (ProviderRequest, ключей в нём нет), сырой ответ;
                      текст — после вычистки секретов (§9)
  .rptg/lock          замок одного писателя: круг и ответы пользователя — командой или в окне
  src/                собранная программа: пакет, тесты, run_tests.py (`rptg export`, сама по окончании `run`)
~/.rptg/ (или RPTG_HOME)
  trusted.json        доверенные проверки — итог `rptg selftest` (Config.trusted)
  competence.json     таблица компетенций
```

Раскладка по объектам (`cards/`, `designs/`, `evidence/` отдельными файлами) — когда состояние станет
большим. Ключи API — только в переменных окружения (`RPTG_KEY_<ОПЕРАТОР>`, иначе ключ поставщика); в
файлы они не пишутся, и в песочницу их не передаёт белый список окружения. Тексты вызовов проходят вычистку
секретов тем же списком, что в PTG-MEM. Писатель состояния один: второй процесс получает отказ «проект занят», а
не перезапись чужого перехода (замок снимает ОС и при смерти процесса).

Узел идентифицируется путём от корня: `app`, `app.billing`, `app.billing.tax`,
`app.billing.tax.rates`. Операция — `узел:операция`. Пакеты Python повторяют дерево:

* каждый составной узел — пакет со сгенерированными схемами;
* каждый лист — модуль с его функциями.

## 4. Конвейер {#pipeline}

```
замысел + приёмочные примеры
   │
   ▼ КАРТА        архитектор: текст карты с эскизом всех ветвей, типы,
   │              карточка корня, разложение корня (следующие уровни — по назначению)
   ▼ проверки     П1 П2 П3 П4 П7 на разложении корня (+П5 без блокировки)
   ▼ УТВЕРЖДЕНИЕ  пользователь смотрит карту в окне: «да» или «нет с комментарием»
   │
   ▼ РАЗЛОЖЕНИЕ   сверху вниз, пока есть составные узлы без разложения:
   │                route: вид узла («сначала целиком»), класс работы, оператор
   │                конструктор: дочерние карточки + схемы потоков узла
   │                проверки П1–П4, П7 против карточки узла
   ▼ ИСПОЛНЕНИЕ   каждая функция листа: route выбирает оператора → код → Э1 Э2 Э3
   ▼ СБОРКА       снизу вверх: составной узел, когда приняты все его дети →
   │              codegen пишет соединения из схемы → Э6 узла
   ▼ ПРИЁМКА      корень: сквозные примеры пользователя, свойства, пробный запуск
   ▼ готово
```

**Отказ проверки** обрабатывается по роду нарушения:

* **форма** — тот же оператор, другая формулировка;
* **совпавший ответ** — смена зерна;
* **содержание** — одна починка с отчётом, затем следующая ступень лестницы;
* **лестница кончилась** — у функции повышение узла до составного, у разложения подозрение на
  карточку её владельцу;
* **одинаковый провал двух разных операторов** — подозрение сразу.

Точные правила — [LOGIC.md §6–§8](LOGIC.md#routing).

**Круг оболочки** (с постройки `rptg.plan`, 01.10.2026) — последовательный:
`plan_next → действие → событие → apply_event → plan_next`. Ядро чисто: выбор действия ничего не
пишет, состояние меняет только переход, состояние `writing` ядро не ставит — пока вызов в пути,
элемент стоит там, где его оставил прошлый переход, и ответ приходит к той же позиции. Действия и
события:

* `call_model` → ответ модели (`model_answered`); совпавший по хэшу ответ — не попытка: при новом
  вызове того же задания оболочка меняет зерно — у OpenAI-подобных и llama.cpp `seed`, у Google
  `config.seed`. У Anthropic зерна нет, а температуру Opus 5.5 не принимает (400): повтор уходит как есть,
  потолок повторам — BUDGET политики. При жадной выборке (температура 0) смена зерна не помогает;
* `run_sandbox` с целью и прогоном (`e1_mypy`, `e2_e3`, `e6`, `smoke`) → `sandbox_finished` (§6);
* `ask_user` — утверждение `{approve, design_hash}` (ответ `{…, decision: yes|no, comment}`),
  решение `{decide, reason, reports}` (`decision: retry|revise`) или перепроверка
  `{recheck, reason: unknown}` → `user_answered`;
* `pause` с причиной, `stop`; команды пользователя `pause`, `resume`, `budget` — событием `command`.

Доверие проверок ставит оболочка: по итогу контрольных случаев `check` она пишет список доверенных в
`Config.trusted`. Без него каждый pass — «не знаю», и ядро спрашивает пользователя, а не принимает
(ERROR ≠ FAIL). Сквозной круг программы накладных от замысла до DONE — контрольный случай plan:
5 ответов моделей, одно утверждение, 6 прогонов песочницы.

Пользователь может в любой момент:

* закрепить оператора за узлом, поддеревом или уровнем;
* пометить узел «лист» или «раскладывать»;
* добавить эталонный пример на любой узел;
* потребовать своего утверждения для любого поддерева.

## 5. Модели, роли, маршрутизация {#llm}

### 5.1. Модели и поставщики

В `project.yaml` модель задаётся коротким именем и адаптером:

```yaml
models:
  opus:   {provider: anthropic, model: claude-opus-5}
  astra:  {provider: openrouter, model: "<имя из каталога>"}
  gpt:    {provider: openai, model: "<имя из каталога OpenAI>"}
  gemini: {provider: google, model: "<имя из каталога Google>"}
  grok:   {provider: openrouter, model: "<x-ai/…>"}
  mini:   {provider: openrouter, model: "<openai/…-mini>"}
  local:  {provider: openai_compatible, base_url: "http://127.0.0.1:8080/v1", model: qwen-coder}
  gguf:   {provider: llamacpp, path: "H:/models/qwen2.5-coder-7b-q4_k_m.gguf"}
```

| адаптер | через что | структурный вывод |
|---|---|---|
| `anthropic` | официальный Anthropic SDK | схема — вход инструмента `answer` без `strict`, выбор `auto`; длинные ответы потоком. Строгий вывод (`output_config.format`, `strict`-инструменты) ответов rptg не вмещает (ниже) |
| `openai` | официальный OpenAI SDK | `response_format` с JSON Schema без `strict` или функция `answer` |
| `google` | официальный SDK Gemini | `response_json_schema` в `config` (не сверено с живым API) |
| `openrouter`, `openai_compatible` | один адаптер OpenAI-совместимого протокола: OpenRouter, xAI, DeepSeek, локальные серверы (llama.cpp server, Ollama, vLLM) | как у `openai`; `endpoint` — адрес OpenRouter или `base_url` оператора |
| `llamacpp` | `llama-cpp-python` в процессе | ограничение вывода грамматикой из JSON Schema; у функции — грамматика одного блока `python` |

**Что поставщики умеют на самом деле** (находка постройки `talk`, 29.09.2026). Строгий
структурный вывод Anthropic принимает только закрытые записи (`additionalProperties: false`
везде), без рекурсии и без словарей. У каждого ответа rptg есть словари (`flows`, `args`,
`fields`) и непрозрачный JSON (входы и выходы примеров, схемы типов): надмножества допустимых
ответов в этих пределах нет. Строгий режим OpenAI вдобавок требует всех полей обязательными.
Поэтому:
* `json_schema` у Anthropic недоступен;
* у OpenAI-подобных он идёт без `strict`;
* ограничение по полной схеме даёт только грамматика llama.cpp.

Способ, которым сделан запрос, — первый доступный поставщику из предпочтений способа оператора
([LOGIC.md §8.3](LOGIC.md#tasks)), и он пишется в сам запрос (`ProviderRequest.mode`). У
`llama-cpp-python` есть ловушка: при неудаче перевода схемы в грамматику он **молча** берёт
грамматику «любого JSON». Поэтому оболочка переводит схему сама, через
`LlamaGrammar.from_json_schema`, а контрольный случай `talk` держит перевод обеих схем ответа.

**Смоук локальной модели — до калибровки** (мицелий, `MODELS_ONBOARDING.md` §3–§5; ошибка там
стоила целого прогона и видна только по косвенным признакам). `talk` шлёт канонический диалог:
системная часть и ход пользователя. Как он станет токенами, решает шаблон чата модели, поэтому
оболочка до первой задачи оператора смотрит глазами:
* **собранный промпт после шаблона.** Инструкция на месте. У модели без системной роли (Gemma)
  она внутри хода пользователя, а не выброшена молча. Спецтокены не задвоены — двойной BOS
  незаметно портит качество;
* **сырой ответ.** Нет продолжения диалога за себя: иначе не объявлен стоп-токен (`<end_of_turn>`
  у Gemma, `<|eot_id|>` и `<|end_of_text|>` у Llama 3);
* **метаданные GGUF.** `tokenizer.chat_template` есть и действительно применяется.

Складывать системную часть в ход пользователя всем подряд нельзя: каждая модель должна получить
свой канонический формат с одним и тем же содержанием. Модели с рассуждением (Qwen3) без
`/no_think` уходят в `<think>` и выедают весь предел (замер мицелия: 384 токена из 384). В
`llama-cpp-python` 0.3.34 переключателя `enable_thinking` нет. При `grammar` мыслям места нет:
грамматика требует ответ с первого токена.

Мысли в тексте ответа снимает П1 (LOGIC §5). Модель без смоука в таблицу компетенций не входит.

**Оператор** — модель плюс то, что меняет её поведение: адаптер и настройки, версия подсказок,
роль. Измеряется и маршрутизируется именно оператор: изменил подсказку — получил другого оператора
(D16).

**Профиль оператора** хранит:

* способ структурного вывода: `json_schema` | `tool` | `grammar` | `prompt` — это просьба; какой
  способ исполнен, пишет запрос;
* разложение за один ответ или за три шага: `steps: combined | split`
  ([LOGIC.md §8.2](LOGIC.md#tasks));
* цены входа, выхода и кэша;
* параметры поставщика (мышление, усилие, температура, предел вывода) — в `params`, передаются как
  есть; универсальных значений нет (F3, F4). Отдельных полей окна и предела вывода у профиля нет:
  у Anthropic `max_tokens` обязателен и задаётся в `params`. Пресеты ставят потолок вывода модели при
  потоке по документации Anthropic: 128K у Opus 5.5 и Sonnet 5.5, 64K у Haiku 4.5; в лимит выдачи в минуту
  `max_tokens` не входит — считаются только выданные токены. У `llamacpp` ключи
  `params`, которые принимает только конструктор `Llama` (`n_ctx`, `n_gpu_layers`, `chat_format`…), идут в
  загрузку модели: оболочка делит их по сигнатурам самой библиотеки.

Claude вызывается через адаптер `anthropic`. Кэш и обработка отказов в нём работают полностью,
структурный ответ — через инструмент (выше).

**Что бы ни обещал поставщик, ответ всегда проверяется JSON Schema скриптом**, а сырой ответ
хранится до разбора.

### 5.2. Роли, лестницы, таблица

```yaml
roles:
  architect:   [opus]                         # один или несколько по возрастанию силы
  designer:    [gemini, grok, opus]           # лестница: дешёвая → сильная
  implementer: [gguf, mini, gemini, opus]
routing:
  target: 0.8                                 # доля успеха, которой должен достигать оператор в таблице
  prior_bands:                                # границы прикидки — только пока в таблице нет клетки
    designer:    [45, 70]
    implementer: [30, 55, 75]
  adapt: false                                # адаптация внутри проекта — допущение, выключена
  explore: 0.0                                # доля задач со случайной ступенью для несмещённого журнала
repair: {per_rung: 1, form_retries: 2}
overrides:                                    # ручные назначения — сильнее таблицы и прикидки
  "level:2..3":      {designer: grok}         # уровни 2–3 раскладывает Grok
  "app.billing.**":  {implementer: gemini}    # узел и всё его поддерево
  "app.tax.compute": {kind: final, implementer: opus}
  "app.ui.**":       {designer: opus, approve: true}   # своё утверждение на поддерево
```

`route` решает в таком порядке:

1. ручное назначение;
2. клетка таблицы компетенций для класса работы — самый дешёвый на успех оператор лестницы, который
   достигает `target` на подборе и не падает ниже `target − 0,1` на проверке;
3. прикидка по карточке и `prior_bands`.

При отказах — следующая ступень той же лестницы. То, что она помогает, — допущение А3 из
[BASIS.md](BASIS.md), журнал его проверяет.

Ручное назначение не отменяет только правил, вытекающих из инвариантов: например, узел, которому
есть кого вызывать, не может быть листом. Правила, классы, маски и старшинство —
[LOGIC.md §6](LOGIC.md#routing).

**Конструкторы по умолчанию — сильные модели.** Малые локальные модели в роли планировщика
промахивались: 1,5B выбирала нужную величину в 22 % случаев (LIFE-9). Годен ли конкретный оператор
раскладывать, покажет калибровка разложений (v0.1).

**Калибровка — круг оболочки** (`rptg models calibrate`, ядро — с постройки `rptg.bench`,
01.10.2026): `calibration_plan` делит эталонный набор на подбор и проверку и даёт задачи — каждый
оператор на каждой задаче; оболочка зовёт модель (`talk`), собирает функцию и гоняет скрытые тесты в
песочнице, пишет итог `{item, class, operator, passed, cost, finish_reason}` — цену даёт `talk.cost`;
`competence` превращает итоги в таблицу и гейт G0. Перезапуск задачи заменяет прежний итог. Правила
раздела, победителя рода, цены на успех — [LOGIC.md §6.4](LOGIC.md#routing).

### 5.3. Кэш, учёт, отказы

* **Кэш:** правила роли и схема формата — стабильный префикс. У Anthropic — явная метка кэша,
  у других поставщиков — как они умеют. Попадание в кэш учитывается там, где поставщик его
  сообщает.
* **Учёт:** токены, деньги и `finish_reason` по оператору, роли, узлу и попытке; цены из профиля.
  Входные токены — те, что по полной цене: у Anthropic `input_tokens` и запись в кэш, у остальных
  вход минус прочитанное из кэша; прочитанное из кэша — отдельно, по цене кэша. Мысли Gemini
  идут в выход. Надбавки за запись в кэш (у Anthropic 25 %) в `Price` нет: запись считается по
  цене входа. Бюджет на проект, фазу, роль и задачу; превышение → пауза и вопрос пользователю.
  Цены Claude в пресетах — открытые данные Anthropic (platform.claude.com/docs/en/about-claude/pricing,
  сверено 04.10.2026): вход, выход и чтение из кэша за миллион токенов; у локальных моделей — 0, у
  заготовок без модели — «0», и `rptg new` их называет.
* **Отказ модели** — отдельный исход, не «плохой код». Для Claude серверные замены при отказе
  включаются в профиле оператора (бета-возможность API).

## 6. Проверки (`verify`) {#verify}

Интерфейс один: предмет + контекст → доказательства:

```
{check, layer, subject, subject_hash, class: HARD|SOFT, verdict: pass|fail|unknown,
 details, counterexample, tool, tool_version, trusted, seconds}
```

| слой | где | что | чем |
|---|---|---|---|
| П1 форма | каждое разложение и каждая карточка | извлечение ответа из сырья; JSON Schema; условия разбираются и типизируются; короткие имена разрешаются однозначно | jsonschema, cond |
| П2 структура | каждое разложение; I10 — всё дерево в конце | инварианты дерева и схем потоков: источники, использование выходов, без циклов, видимость и `uses`, пределы глубины и детей, прогресс разложения, неизменность чужих карточек и примеров пользователя, достижимость | networkx |
| П3 данные | каждое ребро потока | тип источника ⊑ тип назначения | jsonsubschema |
| П4 условия | каждое ребро потока; каждая операция | факты выше по потоку ⇒ требования вызываемого; выполнимость и непротиворечивость | Z3 |
| П5 (без блокировки) | каждая операция составного узла | факты потока ⇒ гарантии узла | Z3 |
| П7 примеры | каждая операция | примеры, включая пользовательские, удовлетворяют своим требованиям и гарантиям; число примеров | cond → Python |
| Э1 статика | каждая функция листа | одна функция по сигнатуре карточки; импорты и вызовы по белым спискам; запреты; размер и сложность; mypy в строгом режиме | ast, radon, mypy |
| Э2 условия | каждая функция листа | примеры через обёртку «требования на входе — гарантии на выходе» | codegen + sandbox |
| Э3 свойства | каждая функция листа | Hypothesis через ту же обёртку | hypothesis + sandbox |
| Э6 сборка | каждый составной узел, снизу вверх; корень — с пробным запуском | соединения из схемы; примеры и свойства узла на собранном коде; сверка импортов с планом; **распределение вины** по трассе обёрток — кто чинит | codegen + sandbox + ast |

**Договор с оболочкой для Э1–Э3 и Э6** (с постройки `rptg.build`, 30.09.2026). Ядро отдаёт набор
файлов (`build_files`), оболочка пишет его во временную папку песочницы и запускает
`python run_tests.py <что>` из её корня: `e1_mypy` → `mypy`, `e2_e3` и `e6` → `tests`, пробный запуск
корня → `all`. Прогонщик сам пишет `report.json` рядом (LOGIC §5, Э6); оболочка возвращает ядру
событие `sandbox_finished` с кодом выхода, признаком тайм-аута, отчётом и хвостом stderr — и больше
ничего не разбирает. Код 2 без отчёта — сбой оснастки, вердикт `unknown`, а не провал функции. В
песочнице стоят `hypothesis` и `mypy`; тайм-аут — оболочки. Прогонщик и среда `_rt.py` — данные
разложения `rptg.build`: правка их текста — правка разложения, с новым хэшем. С 01.10.2026 прогонщик
сверяет и чистоту: вход в JSON до вызова и после; вызов, изменивший свой вход, — нарушение стороны
`purity` испытуемой операции (`cond` — «параметры не меняются: <имена>»), в той же записи
`violation`, что нарушения условий (LOGIC §5, Э2).

**Контрольные случаи.** У каждой проверки есть набор заведомо годных и заведомо негодных предметов
с известным вердиктом. Набор гоняется при запуске и в CI. Проверка, не прошедшая его, получает
`trusted: false`, и её доказательства в приёмку не идут.

**Что значит HARD здесь.** Карточки ниже корня пишут модели. Поэтому HARD-вердикт отвечает на
вопрос «соответствует ли результат карточке». На вопрос «верен ли он замыслу» отвечают примеры
пользователя: на корне — всегда, на других узлах — там, где пользователь их добавил.

## 7. Окно (`gui`) {#gui}

Локальный сервер на 127.0.0.1, доступ по токену — как в PTG-MEM.

* **Карта сети** — дерево разложения, раскрывается на любую глубину. Цвет — состояние: серый —
  запланирован, жёлтый — в работе, зелёный — принят, красный — отказ, фиолетовый — подозрение на
  карточку. Метка — какой оператор назначен и почему: ручное назначение, таблица или прикидка.
* **Схема потока узла** — как технологическая схема. Узлы-вызовы и линии-значения с именем и
  типом; щелчок по линии показывает условия на концах и результат П3 и П4.
* **Назначения:** закрепить оператора за узлом, поддеревом или уровнем, пометить «лист» /
  «раскладывать», поставить утверждение на поддерево. Для каждого ребра видно, какой оператор его
  провёл.
* **Примеры пользователя:** добавить эталонный пример к операции любого узла.
* **Карточка, ревизии, доказательства, контрпримеры.**
* **Таблица компетенций** — только по калибровке, с объёмом выборки. Исходы рабочих прогонов
  показываются отдельно и с пометкой «не для сравнения операторов»: на старшие ступени доходят
  только трудные задачи.
* **Разложение — индикаторы качества** (DECOMPOSITION_MODEL §6): ветвление, доля операций с
  примерами пользователя, доля `unknown`, размер детей относительно родителя.
* **Расходы** — по операторам и ролям; стоимость починок поддерева рядом со стоимостью его
  пересборки.

**Сделано** (`rptg gui`, 04.10.2026; `rptg_host/gui.py`, `gui.html`, без внешних зависимостей): сводка,
вопрос ядра с ответами (утвердить, отклонить с комментарием, повторить, ревизия, перепроверить,
продолжить), запуск и остановка круга (круг — в потоке, останавливается между шагами), дерево сети с
цветами и меткой назначения, узел — карточка, элементы с недостающими слоями и ожиданием, отчёты, схемы
потоков списком, исходы прогонов, ручное назначение маской (пишет `project.yaml`, оператор — из
лестницы роли; маска — по грамматике LOGIC §6.6, новый `project.yaml` читается как Config до записи).
Доступ — как в PTG-MEM: токен во фрагменте адреса (на сервер не уходит; страница держит его в
sessionStorage и очищает адрес) и в заголовке X-Token каждого запроса API; Host только свой (подмена DNS).
Окно отправляет ядру те же события, что команды, и держит тот же замок проекта. Дальше: схема потока рисунком с
условиями на линиях, добавление примеров пользователя (нужно событие ядра), индикаторы качества
разложения, ревизии.

## 8. Командная строка (`cli`) {#cli}

```

rptg models test <имя>                                      отвечает ли оператор строгим JSON
rptg models calibrate <имя>… [--set functions]              калибровка на эталонном наборе
rptg selftest                                               контрольные случаи всех проверок
```

Сделано в оболочке 04.10.2026: `new`, `run`, `approve`, `decide`, `recheck`, `pause`, `resume`,
`budget`, `status`, `show`, `graph`, `outcomes`, `export`, `selftest`, `gui` (`python -m rptg_host …`).
Дальше: `models test` (строгий JSON и смоук шаблона чата у локальных), `models calibrate`, `assign`,

Готовые наборы моделей при создании проекта:

* `claude` — только Claude: Opus 5.5, Sonnet 5.5, Haiku 4.5 с ценами по открытым данным Anthropic;
* `mixed` — пример смешанной лестницы;
* `local` — только локальные модели, разложение по шагам (`steps: split`). Предупреждение при
  создании: малые модели в роли конструктора промахиваются (LIFE-9), для этой роли нужна самая
  сильная локальная модель из доступных.

Любой набор потом правится в `project.yaml` или в окне.

## 9. Безопасность и надёжность {#safety}

* **Недоверенный код:** статические запреты по умолчанию — `os`, `subprocess`, `socket`,
  `ctypes`, `importlib`, `eval`, `exec`, `__import__`, открытие файлов, доступ к `__*__`.
  Разрешения — только через объявленные эффекты (`fs.read`, `fs.write`, `stdout`, `clock`,
  `random`). Тесты — только в песочнице. Ограничений на уровне ОС в MVP нет, пользователь
  предупреждается (`rptg new`).
* **Ключи** — из окружения или профилей поставщиков, в `.rptg/` не пишутся. Тексты попыток проходят
  вычистку секретов.
* **Сбои** — атомарная запись, журнал только дописывается, незавершённая задача повторяется; строку
  журнала, оборванную при аварии, чтение пропускает.

## 11. Нефункциональные требования MVP {#nfr}

* **Размер:** до ~500 узлов, глубина до 8, до 7 детей у узла. Все три предела — настройки
  проекта.
* **Время проверок:** П4 на одно обязательство — тайм-аут 2 с; проверки одного составного узла —
  меньше 30 с; одного листа — меньше 30 с.
* **Платформы:** Windows 10 — основная; CI на Windows, macOS и Linux.
* **Модели:** цель — эталонный проект собирается целиком на локальных моделях, медленнее и с
  большим числом починок. Это проверяется замером на эталоне, а не обещается заранее. Главный
  риск — роль конструктора (LIFE-9).

## 12. Как проверяется сам продукт {#evaluation}

rptg — это конвейер из ролей, а оркестрация в прошлых опытах проекта проигрывала простому
best-of-N:

* F46: артефактный конвейер не превзошёл best-of-N при равных токенах;
* OLD-1: 29 % против 52 % на 200 задачах MBPP.

Поэтому ни одно утверждение о продукте не публикуется без замера против плоского базиса.

**Базис:** одна сильная модель пишет программу целиком. Для честности она получает те же проверки
как обратную связь — те же примеры пользователя и тот же бюджет попыток.

**Условия:**

* равный бюджет, проверенный **повызовно**: ни одно плечо не упирается в предел вывода там, где
  другое не упирается; `finish_reason` в каждой записи;
* **целевой режим:** программы больше, чем надёжно пишется за один ответ. Если базис ни разу не
  упёрся в предел, замер ничего не говорит о средстве его обхода;
* пороги успеха и провала фиксируются **до** прогона;
* отдельно меряется разложение (OQ-DEC-1): доля разложений, принятых проверками, доля подозрений,
  итог на примерах пользователя.

Что ожидается честно, по прошлым данным:

* ремонт по сигналу HARD-проверки дешевле плоского best-of-N — в experiment10 в 2,4–2,7 раза при
  равном успехе;
* но он «эффективнее, а не способнее»: потолок ремонта был ~73 % против 76,7 % у best-of-N = 4.

Порядок всех замеров — [BASIS.md §4](BASIS.md).
