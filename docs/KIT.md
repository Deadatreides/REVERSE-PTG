**Своё (склейка):**
- правило видимости зависимостей по дереву карточек;
- сверка примеров с условиями до кода. Готового нет: заглушка отвечает ожиданием примера, а условия во время doctest проверяет сам deal;
- билеты задач и лестница моделей;
- вклейка тел: исполнитель не может тронуть карточку.

## Как устроено

- **Карточка** — модуль Python:
  - узел — модуль, лист — `<имя>.py`, составной — `<имя>/__init__.py`;
  - в описании модуля — `node: leaf|composite`;
  - у каждой функции: подпись с типами, `@deal.pre`, `@deal.ensure`, `@deal.has`;
  - в описании функции: `D: <число решений>` и примеры doctest;
  - тело — `raise NotImplementedError`.

  Импорты модуля объявляют, чем узел может пользоваться: типами, детьми, братьями и тем, что может родитель.
- **Порядок:**
  1. Главный чат (Opus) — архитектор. Он пишет `spec.md`, затем корень, `types.py` и детей корня.
  2. Пользователь утверждает корень.
  3. Составные узлы раскладывает проектировщик (субагент sonnet).
  4. Листья пишет исполнитель (субагент haiku), когда готово всё, что лист импортирует.
  5. Составной узел собирается, когда готовы его дети: его примеры и свойства гоняются с настоящими детьми.
- **Проверки на каждой сдаче** идут в копии программы, в настоящую попадает только принятое:
  - разложение — mypy, tach, ruff, deal lint, видимость, сверка примеров с условиями;
  - код — mypy, tach, ruff, deal lint, radon, doctest, deal.cases, CrossHair.

  Отчёт инструмента уходит модели как есть, и модель чинит сама: до 3 сдач на билет.
- **Лестница:**
  - код — haiku → sonnet → opus;
  - разложение — sonnet → opus.

  Если лестница исчерпана, карточку чинит её владелец, проектировщик родителя. Если исчерпаны и починки (2) — вопрос
  пользователю (`kit_unblock`). Новая версия корня — снова на утверждение.
- **Состояние** — `<проект>/.rptg-kit/`:
  - `state.json` и `journal.jsonl`;
  - `trash/` — сюда уходят заменённые файлы, ничего не удаляется.

  Настройки готовых проверок остаются в программе: `pyproject.toml`, `tach.toml`, `tests/test_rptg_cases.py`.
  Границы держатся и после kit: `python -m pytest`, `python -m tach check`.

## Подключение

Готовые проверки стоят в отдельном окружении `.venv-kit` в папке kit: `pip install -r requirements-kit.txt` (deal 4.24.6,
crosshair-tool 0.0.111, tach 0.35.3, ruff 0.17.0).

**Окружение проверок программы** (с 11.10.2026):
- Если в папке проекта есть `.venv`, kit проверяет им. Иначе — окружением сервера kit.
- В копию программы `.venv` не копируется. Каким интерпретатором проверять, копия знает из файла `.rptg-python`.
- До проверок kit сверяет, есть ли в окружении всё нужное: пакеты, которые импортирует программа, и сами проверки.
  - Нехватка даёт отчёт `[env]` с командой установки. Сдача не засчитывается, до двух раз на билет.
  - Субагент отвечает «сдался: окружение»; главный чат ставит пакет и возвращает того же субагента.
  - Если пакета не хватает при сборке составного узла, `kit_next` отвечает `kind: env`, и узел на починку не уходит.
- Пакеты, которые импортирует программа, kit пишет в `dependencies` её `pyproject.toml`.

**Свойства при связанном условии pre.** Пример — `0 <= start < end <= len(text)`. Hypothesis идёт только по тем
входам, что прошли условие, без порогов «медленно» и «много отброшено». Если не прошёл ни один вход
(Unsatisfiable), тест пропускается с причиной, и свойства проверяет CrossHair.

**Функции с побочными эффектами** (`@deal.has("io" | "write" | …)`) не получают случайных входов и решателя: Hypothesis
подсовывал бы им случайные пути. Их проверка — примеры, а примеры идут в одноразовой копии программы.

**Роли** перечисляют разрешённые инструменты: инструменты kit (`kit_brief`, `kit_submit`, `kit_guide`, `kit_status`,
под обоими именами — плагином и через `.mcp.json`), а также Read, Grep, Glob, ToolSearch. Роли, загруженные в уже
открытом чате, обновятся только в новом чате.

**Плагином** — сервер и роли во всех чатах. Один раз:

```
/plugin marketplace add Deadatreides/REVERSE-PTG
/plugin install rptg@rptg-local
```

Локальная папка тоже годится: `claude plugin marketplace add <путь к REVERSE-PTG>`. Затем новый чат. Роли там
называются `rptg:rptg-designer` и `rptg:rptg-implementer`.

Claude Code держит копию плагина в `%USERPROFILE%\.claude\plugins\cache\rptg-local\rptg\<версия>\`, хотя
`plugin list` пишет «Read from: <папка>». Так выяснилось 11.10: копия 0.1.0 была снята до исправления ввода, и
проверки под Claude Code висели.

С 0.2.0 сервер запускается через `rptg_kit/launch.py`.
* Папку kit он берет из `~/.rptg-kit/home`, если там записан путь к рабочей копии, иначе папку самого плагина.
* Python берет так: `RPTG_KIT_PYTHON`, иначе `.venv-kit` этой папки, иначе тот, которым запущен.

Отсюда:
* **правка кода kit** в рабочей копии применяется с новым чатом;
* **правка ролей или навыка** — с новой версией в `plugin.json`, затем
  `claude plugin marketplace update rptg-local` и `claude plugin update rptg@rptg-local`.

**Только в одну папку проекта** — `.mcp.json` и `.claude/agents/`:

```bash
<REVERSE-PTG>/.venv-kit/Scripts/python <REVERSE-PTG>/rptg_kit/connect.py <папка>
```

Затем новый чат в этой папке; Claude Code спросит разрешение на сервер rptg.

**Дальше — фраза соседнему чату:** «разработай ПО по ТЗ `<файл>` в папке `<папка>`».

## Правила для Claude: токены

Дорог главный чат. Эти правила — в подсказке сервера, в навыке `develop` и в [CLAUDE.md](../CLAUDE.md):
1. Вышестоящая модель получает сигнал только в конце: итог прогона или сторож молчания.
2. Запустив раннер и сторожа, закончить ход и до выхода сторожа ничего не вызывать.
3. Без раннера — волны целиком в фоне, уведомления отдельных субагентов не разбирать.
4. Архитектор пишет только карточки, в свежем чате с малым контекстом.
5. Проверки гоняет kit; модели запускают только итоговый `pytest` после `done`.
6. Исполнители отвечают одной строкой.
