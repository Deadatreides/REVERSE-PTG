# Обратный PTG — логическое описание MVP

**Версия 0.3 от 27.09.2026.** Устройство программы — в [ARCHITECTURE.md](ARCHITECTURE.md), факты и
допущения, на которых стоят правила, — в [BASIS.md](BASIS.md). Здесь описано, **что** и **по
каким правилам** делает скрипт.

**Что изменилось против 0.2 после сверки с базой PTG:**

* **Вид узла — «сначала целиком».** Узел раскладывается только по необходимости: есть кого
  вызывать, много операций, не помещается в функции допустимого размера, лестница исполнителей не
  справилась. Правило «выглядит сложным → раскладывать» снято (F28, LIFE-9, experiment14 G2 = 0).
* **Маршрут — по классу работы и измеренной таблице компетенций** (experiment14: +0,38).
  Формула оценки по карточке осталась только для холодного старта (допущение А1).
* **Прогресс разложения:** каждый ребёнок строго меньше родителя по оценке размера, детей немного
  (E6/G1).
* **Починка без прежнего ответа целиком.** Нарушение формы идёт отдельным путём — переформулировкой
  (experiment11, experiment12). На ступени одна починка содержания, а не две.
* **Раннее подозрение** распространено на примеры и свойства: одинаковый провал двух разных
  операторов — признак ошибки в карточке (F11).
* **«Принят» значит «соответствует карточке».** Корректность относительно замысла подтверждают
  только примеры пользователя (SEAM_MODEL §2.2). Такие примеры можно прикрепить к любому узлу.
* **У каждой проверки есть контрольные случаи** (F45, arch1).

## 1. Сущности {#entities}

| сущность | что это | ключевые поля |
|---|---|---|
| **проект** | целевая программа | замысел, приёмочные примеры пользователя, операторы, роли и лестницы, ручные назначения, пределы, бюджет, имя пакета |
| **узел** | элемент программы на любом уровне: сама программа, подсистема, модуль, группа функций | путь, родитель, уровень, назначение, интерфейс (операции), `uses`, эффекты, разрешённые импорты, оценка размера `est_lines`; вид — **составной** или **финальный** |
| **операция** | единица поведения узла | имя, описание, параметры, результат, `requires`, `ensures`, эффекты, примеры |
| **пример** | вход и ожидаемый выход операции | `in`, `out`, источник: **пользователь** (эталон замысла) или **модель** (часть договора); сравнение `match`: `exact` (по умолчанию) или `subset` — только указанные поля, строка `"*"` означает «любое значение» (С-4) |
| **схема потока** | как составной узел выполняет одну свою операцию через операции детей и узлов `uses` | узлы схемы, источники, результат |
| **функция** | код одной операции финального узла | ровно одна функция Python |
| **тип** | именованная структура данных | подмножество JSON Schema: объект, список, **словарь** (`additionalProperties`), строка и перечисление, целое, число, логическое, необязательное; ссылка на тип — `{$ref: Имя}`; встроенные `Decimal` (десятичное записью) и **`Json`** — непрозрачное значение; `oneOf` строки и объекта — только для записи источника в схеме потока. В параметрах допустимы простые имена `string`, `integer`, `number`, `boolean` (С-2). Владелец — узел, в чьём разложении тип создан |
| **карточка узла** | интерфейс узла | всё из строки «узел»; пишет тот, кто раскладывал родителя |
| **разложение** | внутреннее устройство составного узла | карточки детей, новые типы, схема потока на каждую операцию узла |
| **оператор** | то, чей успех измеряется | модель + адаптер и настройки + версия подсказки + роль (arch0 MODEL_INTERFACE §2) |
| **роль** | архитектор, конструктор, исполнитель | лестница операторов |
| **класс работы** | на что делятся задачи при маршрутизации | роль; у функций ещё и род (§6.3) |
| **таблица компетенций** | измеренный успех операторов по классам | доля успеха, объём выборки, цена на успех; подбор и проверка раздельно |
| **назначение** | кто и как делает работу по узлу | вид узла, оператор, ступень, источник решения: правило, ручное, таблица, априорная оценка, адаптация, повышение |
| **задача, попытка** | работа и один вызов по ней | оператор, хэш подсказки, **сырой ответ до разбора**, расход, `finish_reason`, вердикт |
| **доказательство** | результат одной проверки | проверка, слой, предмет, хэш предмета, класс (HARD/SOFT), вердикт, подробности, контрпример, версии инструментов |
| **ревизия** | новая версия карточки или разложения | номер, предыдущая версия, причина, автор; старая версия не удаляется |
| **утверждение** | решение пользователя | хэш утверждённого разложения; «да» или «нет» + комментарий |
| **исход** | итог задачи | оператор, класс, признаки, ступени, попытки, итог, цена, время, признак «разведка» (§6.8) |

**Идентификаторы:**

* узел — путь от корня через точку: `app`, `app.billing`, `app.billing.lines`;
* операция — `узел:операция`: `app.billing:make_invoice`;
* уровень корня — 1, уровень ребёнка — уровень родителя плюс 1;
* предмет работы — `вид:узел[:операция]`: `map:app`, `design:app.billing`,
  `function:app.money:add`, `assembly:app` (С-11).

## 2. Модель потоков {#flow-model}

### 2.1. Почему потоки

Замысел автора — полная графовая связь всех элементов: что кому и как передаёт и во что из чего
перерабатывает. Если соединения живут внутри кода, который пишет модель, граф можно только
надеяться проверить. Поэтому узлы двух видов:

* **составной узел** — у него есть дети, а каждая его операция — схема потока из операций детей и
  узлов `uses`. Кода в нём нет: соединительный код пишет скрипт. **Здесь живут все рёбра.**
* **финальный узел (лист)** — детей нет, каждая его операция — функция, которую пишет исполнитель.
  Функция **не вызывает кода проекта**: только встроенное и разрешённые импорты. **Здесь живёт
  весь код.**

Каждое место, где одно значение передаётся другому, — ребро схемы потока. Каждое ребро
проверяется по типам (П3) и условиям (П4) ещё до кода.

Исполнитель не может тронуть рёбра физически: он получает карточку одной операции и возвращает одну
функцию.

**Почему именно так, а не «модели договорятся».** SWE1: у разрезанной на дисциплины задачи
сломанные ссылки нашлись в 0,50 патча против 0,05 у одного исполнителя. Несходящиеся имена были
выдуманы. Проверка, которая только фиксирует такие швы, их не спасает. Здесь несходящееся имя
невозможно по построению.

### 2.2. Дерево

```
уровень 1  app                              составной   раскладывает архитектор
уровень 2  ├─ app.billing                   составной   конструктор
уровень 3  │   ├─ app.billing.lines         финальный   исполнители
уровень 3  │   └─ app.billing.tax           составной   конструктор
уровень 4  │       ├─ app.billing.tax.rates финальный   исполнители
уровень 4  │       └─ app.billing.tax.rules составной   конструктор
уровень 5  │           └─ …                 и так далее, пока узлы не станут финальными
уровень 2  └─ app.money                     финальный   исполнители
```

* Глубину ограничивает только предел проекта `max_depth` (по умолчанию 8).
* Вид узла — составной или финальный — определяет правило §6.2, а не место в дереве.
* У финального узла от 1 до `final_max_ops` операций (по умолчанию 6).
* У составного — от 0 до `max_children` детей (по умолчанию 7: «атомов мало»). Ноль детей
  возможен, если его схемы только связывают операции узлов `uses`.

### 2.3. Узлы схемы потока

| узел | запись | что производит |
|---|---|---|
| **вызов** | `{id, call: <операция>, args: {параметр: источник}}` | результат операции |
| **отображение** (цикл по списку) | `{id, map: <операция>, over: <источник-список>, item: <элемент>, args: {…}}` | список результатов той же длины |
| **свёртка** (цикл с накоплением) | `{id, fold: <операция>, over: <источник-список>, init: <источник>, acc: <параметр>, item: <элемент>, args: {…}}` | итоговое накопленное значение |
| **запись** | `{id, record: <тип>, fields: {поле: источник}}` | значение типа-записи; код — скрипта |

**Операция в схеме** записывается относительно узла, которому схема принадлежит:

* `lines:line_total` — операция ребёнка;
* `money:add` — операция узла из `uses`;
* если у узла одна операция, её имя можно опустить: `lines`.

Короткие имена скрипт ищет сначала среди детей, потом среди `uses` и хранит полными:
`app.billing.lines:line_total`. Неоднозначное имя — нарушение П1.

**Источник** — одно из трёх:

* параметр операции с путём: `order.lines`;
* выход узла схемы с путём: `n2`, `n2.total`;
* литерал `{const: …}`, типизированный по месту назначения;
* элемент отображения или свёртки с путём: `o.goal` (ниже).

**Элемент** (С-15, 28.09.2026) — имя элемента списка `over` в пределах своего узла схемы. Если у
вызываемой операции есть параметр с этим именем и `args` его не питают, элемент идёт в него — так
было до С-15: `{map: lines, over: order.lines, item: line}`. Кроме того, `args` могут брать поля
элемента. Это нужно, когда у операции несколько меняющихся параметров, например
`{map: lang:cl_prove, over: n2.proofs, item: o, args: {facts: o.facts, goal: o.goal, env: o.env,
limits: cfg.limits}}`. Имя элемента не совпадает с параметром операции и с узлом схемы. Без С-15
конвейер «лист готовит задания → схема прогоняет по ним операцию языка» не записать: схема не
умеет разбирать запись.

**Результат** схемы — один источник.

Порядок вычисления — топологический, каждый узел схемы считается ровно один раз, отображение и
свёртка идут последовательно. Ветвлений в схемах MVP нет: выбор делает функция листа, она может
вернуть запись с признаком варианта.

**Приём «вычислить всё, выбрать в листе»** (С-8). Когда схеме нужно выбрать, какую из нескольких
операций применить, она вызывает все, а выбирает лист. Каждая операция обязана на неприменимом
входе отвечать пустым или «неприменимо», а не ошибкой. Цена — лишние чистые вычисления.

Ветвление и повторение в политике — отдельный язык arch2 (§7.3). Схемам продукта они не нужны, а
циклы запрещены в обоих языках.

### 2.4. Видимость и `uses`

Схема потока операции узла X может вызывать только:

1. операции детей X;
2. операции узлов из `X.uses`.

`X.uses` пишет тот, кто раскладывает родителя X, — он же пишет всю карточку X. Допустимы:

* **братья X** — другие дети того же родителя;
* **узлы из `uses` родителя** — так зависимость передаётся вниз явно, уровень за уровнем.

Недопустимы:

* предки — через их схемы возник бы цикл;
* потомки — к ним ходят через детей;
* узлы внутри чужих поддеревьев — инкапсуляция.

У финального узла `uses` пуст: функции не вызывают кода проекта.

**Пример.** Архитектор даёт `app.billing.uses = [app.money]`. Конструктор `app.billing` может
передать `app.money` дальше, своему ребёнку: `app.billing.tax.uses = [app.money, app.billing.lines]`.
Второй элемент здесь — брат `tax`.

**Граф зависимостей:** ребро X → Y, если схемы X вызывают операции Y. Он обязан быть без циклов
(I9). Проверять это достаточно внутри каждого разложения. Из поддерева узла наружу ведут рёбра
только в его `uses`, поэтому любой цикл по дереву сводится к циклу между братьями у какого-то
родителя.

### 2.5. Типы

* Тип создаётся в разложении какого-то узла, и этот узел — **владелец** типа. Архитектор создаёт
  типы в разложении корня.
* Тип виден в поддереве владельца. Типы интерфейса узла X создаёт тот, кто раскладывал родителя X.
  Поэтому их видят и братья X — те, кто его вызывает.
* Менять тип может только владелец — ревизией. Имена типов уникальны во всём проекте.
* **`Json` — непрозрачное значение JSON** (28.09.2026, map.md §12). Любой тип — подтип `Json`,
  обратное неверно: CL и схема внутрь `Json` не заглядывают. Объект, переданный в место типа
  `Json`, схема записывает в JSON. Так работают проверки: ответ модели, вход контрольного случая
  и содержимое хэша — это JSON, а превратить JSON обратно в объекты лист не может (для этого
  нужен код проекта или рефлексия, их запрещает Э1). **Обратно — тоже схема** (01.10.2026, постройка
  `plan`): значение `Json`, переданное в типизированное место (запись, список записей), обвязка
  приводит к типу места и проверяет; не подходит — ошибка на ребре схемы, а не в листе.

### 2.6. Карточки

Ниже карточки показаны как YAML, хранятся они как JSON.

**Карточка узла** — пишет тот, кто раскладывал родителя, здесь архитектор:

```yaml
id: app.billing
parent: app
owner: app                        # чьё разложение создало карточку
purpose: "накладные по подтверждённым заказам"
uses: [app.money]
effects: []                       # верхняя граница поддерева: fs.read | fs.write | stdout | clock | random
allowed_imports: [decimal]        # верхняя граница поддерева
est_lines: 40                     # оценка размера автором карточки; у детей — строго меньше
ops:
  - name: make_invoice
    doc: "накладная по заказу: строки, итог"
    params: [{name: order, type: Order}]
    result: {type: Invoice}
    requires:
      - "len(order.lines) >= 1"
      - "forall l in order.lines: l.qty > 0 and l.price >= 0"
    ensures:
      - "result.order_id == order.id"
      - "result.total.amount >= 0"
    examples:
      - in:  {order: {id: 7, lines: [{qty: 2, price: "10.00", currency: EUR}]}}
        out: {order_id: 7, total: {amount: "20.00", currency: EUR}}
        source: model             # пример договора; пример пользователя помечается source: user
```

Там же архитектор написал карточку брата — `app.money` с операцией
`add(a: Money, b: Money) -> Money`:

* `requires: a.currency == b.currency`;
* `ensures: result.amount == a.amount + b.amount`, `result.currency == a.currency`;
* `est_lines: 8`.

**Разложение составного узла** — пишет его конструктор:

```yaml
node: app.billing
children:
  - id: app.billing.lines
    purpose: "стоимость строки накладной"
    uses: []
    effects: []
    allowed_imports: [decimal]
    est_lines: 5
    ops:
      - name: line_total
        doc: "количество × цена, в валюте строки"
        params: [{name: line, type: InvoiceLine}]
        result: {type: Money}
        requires: ["line.qty > 0", "line.price >= 0"]
        ensures:  ["result.amount == line.qty * line.price", "result.currency == line.currency"]
        examples:
          - in:  {line: {qty: 2, price: "10.00", currency: EUR}}
            out: {amount: "20.00", currency: EUR}
types: []                          # новые типы этого разложения
flows:
  make_invoice:
    nodes:
      - {id: n0, record: Money, fields: {amount: {const: "0"}, currency: "order.lines[0].currency"}}
      - {id: n1, map: lines, over: order.lines, item: line}
      - {id: n2, fold: "money:add", over: n1, init: n0, acc: a, item: b}
      - {id: n3, record: Invoice, fields: {order_id: order.id, total: n2}}
    result: n3
```

**Функция финального узла** — пишет исполнитель: ровно одна функция по карточке одной операции.
Импорты типов добавляет скрипт. Исполнитель импортирует только разрешённое.

```python
def line_total(line: InvoiceLine) -> Money:
    return Money(amount=line.qty * line.price, currency=line.currency)
```

В этом примере есть настоящая дыра — её ловит П4 (§9).

**Примеры пользователя** можно прикрепить к операции любого узла — в окне или в
`examples.yaml`. Это эталон замысла: карточка, которая им противоречит, не пройдёт П7, и её
владелец обязан выпустить ревизию.

## 3. Инварианты {#invariants}

Граф принят, только если держатся все инварианты. Каждый проверяется HARD-процедурой слоя П2, если
не указано иное.

| № | инвариант |
|---|---|
| I1 | ровно один корень; у каждого другого узла ровно один родитель; уровень ≤ `max_depth` |
| I2 | пути узлов уникальны; имена операций уникальны в узле, имена параметров — в операции, имена типов — во всём проекте |
| I3 | у финального узла нет детей и от 1 до `final_max_ops` операций; у составного — не больше `max_children` детей; у любого узла ≥ 1 операция и есть `est_lines` |
| I4 | у каждой операции составного узла есть схема потока; у финального схем нет, на каждую операцию будет функция |
| I5 | каждый параметр каждого узла схемы питается ровно одним источником; каждый источник существует и видим |
| I6 | каждый выход узла схемы используется далее или является результатом |
| I7 | схема потока без циклов |
| I8 | вызовы — только по правилам видимости §2.4; `uses` — только братья и `uses` родителя; у финального узла `uses` пуст. Узел на уровне `max_depth` обязан уметь быть финальным: пустой `uses`, операций не больше `final_max_ops` |
| I9 | граф зависимостей без циклов (проверяется у братьев внутри каждого разложения, §2.4) |
| I10 | каждая операция достижима от операций корня. Проверяется, когда разложено всё дерево; мёртвые операции скрипт удаляет сам (§7.6) |
| I11 | **прогресс разложения:** у каждого ребёнка `est_lines` строго меньше, чем у родителя; ни один ребёнок не повторяет интерфейс родителя — сравниваются хэши операций без учёта имён; если ребёнок один, в схемах есть узлы помимо вызовов этого ребёнка |
| I12 | тип источника ⊑ тип места назначения (слой П3) |
| I13 | на каждом ребре факты выше по потоку влекут требования вызываемого (слой П4) |
| I14 | `requires` выполнимы; `requires ∧ ensures` выполнимы хотя бы для одного результата (слой П4) |
| I15 | у каждой операции ≥ 1 пример; у операций корня ≥ 2, из них хотя бы один — пример пользователя (слой П7) |
| I16 | каждый пример удовлетворяет типам, требованиям и гарантиям своей операции (слой П7) |
| I17 | **владение:** разложение узла X не меняет ничего чужого. Карточка X, карточки предков и их братьев, типы чужих разложений, примеры пользователя совпадают по хэшу с принятыми |
| I18 | **эффекты и импорты:** у ребёнка — подмножество родительских; эффекты операции ⊆ эффектам узла; эффекты операции составного узла ⊇ объединению эффектов вызываемых операций; импорты функции ⊆ разрешённым импортам её узла и импортам её эффектов |

## 4. Язык условий CL {#cl}

### 4.1. Грамматика

```
expr    := impl
impl    := or ( "=>" or )*
or      := and ( "or" and )*
and     := not ( "and" not )*
not     := "not" not | cmp
cmp     := arith ( ( "==" | "!=" | "<" | "<=" | ">" | ">=" ) arith )?
         | arith "in" ( setlit | path )
arith   := term ( ( "+" | "-" ) term )*
term    := unary ( ( "*" | "/" | "%" ) unary )*
unary   := "-" unary | atom
atom    := NUMBER | STRING | "true" | "false" | "null"
         | path | func | quant | agg | "(" expr ")"
path    := NAME ( "." NAME | "[" arith "]" )*
func    := ( "len" | "abs" | "min" | "max" | "startswith" ) "(" expr ( "," expr )* ")"
quant   := ( "forall" | "exists" ) NAME "in" path ":" expr
agg     := ( "sum" | "count" ) "(" expr "for" NAME "in" path ")"
setlit  := "{" literal ( "," literal )* "}"
```

`result` — имя результата, доступно только в `ensures`. Остальные имена — параметры операции.

### 4.2. Типы и допустимые действия

| тип | действия |
|---|---|
| целое | арифметика, сравнения, `abs`/`min`/`max`, `%` |
| число, десятичное | арифметика, сравнения, `abs`/`min`/`max` |
| строка, перечисление | `==`, `!=`, `len`, `in {…}`, `startswith` |
| логическое | `and`, `or`, `not`, `=>` |
| список | `len`, индекс, `forall`/`exists`, `sum`/`count` |
| запись | доступ к полям |
| необязательное | `== null`, `!= null`; доступ к значению — только под условием `!= null` в той же конъюнкции |
| логическое | ещё `==` и `!=` (С-3) |
| словарь | `len`, `ключ in словарь` (С-3); индексировать словарь нельзя |
| `Json` | только `== null` и `!= null`: внутрь непрозрачного значения CL не заглядывает |

Имя поля после точки может совпадать со служебным словом: `result.class`, `example.in`.

Типы выводятся из схем. Несовместимое действие — нарушение П1 с указанием места.

### 4.3. Смысл

* `requires` — конъюнкция своих строк над параметрами.
* `ensures` — конъюнкция над параметрами и результатом. Операция обязана её выполнить, если на входе
  выполнялось `requires`.
* **Ограничения типов** — минимумы, максимумы, перечисления, длины из JSON Schema — неявно
  добавляются к фактам о каждом значении этого типа.
* **Деление на ноль** при вычислении — нарушение условия, а не исключение.

### 4.4. Три компиляции

| цель | правило |
|---|---|
| **Z3** (доказательство, П4) | целое → Int, число и десятичное → Real, строка → String, запись → набор полей, необязательное → пара (признак, значение). **Список — ограниченно:** длина L ≤ K (K = 3 по умолчанию) и элементы e₀…e_{K−1}; `forall` → конъюнкция по i < L, `sum` → сумма с `ite`. **Между узлами передаётся текст SMT-LIB**, а не объекты Z3 — они не JSON; решатель вызывает отдельный лист (С-7) |
| **Python** (исполнение, Э2) | прямая трансляция; десятичные — `decimal.Decimal`; ошибки вычисления → нарушение |
| **Hypothesis** (генерация, Э3) | стратегия из типа; сравнения с целыми константами (`x > 0`, `len(xs) <= 10`) в конъюнкции `requires` и в теле `forall` над путём становятся границами **по пути места**: параметр, поля через точку, элемент списка — `[]` (`forall l in order.lines: l.qty > 0` → `order.lines[].qty ≥ 1`). У нецелого строгое сравнение даёт нестрогую границу (`price > 0` → `≥ 0`), точку отсекает фильтр. Путь с индексом (он об одном элементе), `exists`, «или», импликация и прочее — фильтром |

**Честные пределы.** Доказательство П4 верно для списков длины до K — отчёт так и пишет: «доказано
для длин ≤ 3». Большие длины покрывает Э3. Числа с плавающей точкой Z3 считает точными
вещественными: округление не моделируется, его ловит Э3.

### 4.5. Размер условий

Разбор CL даёт три числа — для априорной оценки (§6.5) и для рода работы (§6.3):

* **узлы разбора** — каждый оператор, вызов функции, квантор, агрегат, путь и литерал считается
  одним узлом; переменная квантора отдельно не считается;
* **кванторы и агрегаты** — `forall`, `exists`, `sum`, `count`;
* **нелинейность** — `*`, `/`, `%`, где оба операнда не константы.

## 5. Проверки {#checks}

Все проверки детерминированы и работают без модели (HARD), каждая порождает доказательство.
`unknown` — например, тайм-аут Z3 — **блокирует** приёмку, но показывается отдельно: «не доказано
за 2 с».

Слои П1–П4 и П7 выполняются **для каждого разложения, на любой глубине, одинаково**. Предмет проверки
— разложение узла X против карточки X.

**Что доказывает HARD в rptg.** Карточки ниже корня пишут модели, поэтому проверки по ним отвечают
на вопрос «соответствует ли результат карточке». На вопрос «верен ли результат замыслу» отвечают
только примеры пользователя (SEAM_MODEL §2.2, F9). Отсюда три следствия:

* правило приёмки (§10) называет вещи своими именами;
* одинаковый провал двух операторов ведёт к подозрению на карточку (§7.3);
* пользователь может добавить эталонный пример на любой узел.

**Контрольные случаи.** У каждой проверки, включая извлечение ответа из сырого текста модели, есть
набор случаев с известным ответом: заведомо годные и заведомо негодные карточки, разложения,
функции. Проверка, не прошедшая свои контрольные случаи, помечается недоверенной и HARD-доказательств
не выдаёт (F45; в arch1 59,6 % первичных FAIL были ложными из-за извлечения вне проверки). Если растёт
доля `unknown`, первыми подозреваются проверки, а не модели (F44).

### П1. Форма

1. Сырой ответ модели сохранён; из него извлечён ответ. Извлекает сама проверка (`check.answer`):
   в arch1 59,6 % первичных FAIL были ложными из-за извлечения вне неё. Извлечение не строже
   договора (сверка с базой 29.09.2026):
   * мысли `<think>…</think>` снимаются до поиска блоков — в них бывают свои блоки кода;
   * у незакрытого `<think>` снимается только тег, если дальше идёт ответ. Так делает Qwen3 с
     `/no_think`; наивная вырезка до конца обнулила в мицелии 29 ответов из 30;
   * метка блока — без учёта регистра, у кода ещё `py` и `python3`;
   * блок без метки принимается, когда помеченных нет.

   В LB2 фильтр строже договора дал ~60 % ложных отказов. Несколько блоков там, где договор
   требует один, — провал формы, а не выбор одного из них: выбирать значило бы гадать (arch1,
   этап 8).
2. Ответ валиден по JSON Schema своего вида (разложение — `Design`, карта — `MapAnswer`), причём
   **записи схем закрыты** (`additionalProperties: false`). Иначе лишний ключ проходит форму и
   роняет загрузку ответа в объекты уже в `plan`.
3. Каждое условие разбирается, проходит проверку типов и имеет логический тип.
4. Типы разрешаются по правилам видимости §2.5.
5. Короткие имена операций в схемах разрешаются однозначно.
6. Параметр — не `result` и не слово Python (Н-1). Переменная квантора не совпадает с параметром
   и `result`: язык такое допускает, но подстановка в П4 задела бы связанную переменную.

Шаг пошагового разложения (`design_r1`–`r3`) проверка пока не поддерживает и даёт `unknown`, а
не `fail`: это ограничение проверки, а не ошибка модели.

**При провале:** поле и сообщение разборщика с позицией. Если ответ оборван (`finish_reason` —
предел длины), это отдельная пометка: обрыв не считается ошибкой модели.

### П2. Структура

По разложению X строится граф: дети, узлы схем, рёбра «источник → параметр узла схемы», `uses`
детей. Проверяются I1–I9, I11, I17, I18. Для циклов используется поиск сильно связных компонент.

Глобальны только две вещи:

* уникальность имён типов — по реестру проекта;
* I10 — один раз, когда разложено всё дерево.

**При провале:** инвариант, путь или цикл, на котором он нарушен.

### П3. Совместимость данных

Для каждого ребра: `тип(источник) ⊑ тип(параметр)`. Путь в источнике (`order.lines`) раскрывается
по схеме. Для результата операции: `тип(источник результата) ⊑ тип(result)`. У записи-узла каждое
поле проверяется отдельно.

**При провале:** ребро и документ-свидетель — он проходит схему источника, но не проходит схему
назначения.

### П4. Совместимость условий (и П5 без блокировки)

Для каждой операции S узла X, узлы её схемы в топологическом порядке:

```
F := requires(S) ∧ ограничения типов параметров S
для узла n (вызов операции C с аргументами-источниками σ):
    обязательство O := requires(C)[параметры ↦ σ] ∧ ограничения типов
    доказать F ⇒ O            (т. е. F ∧ ¬O — невыполнимо)
    если выполнимо → нарушение, контрпример = модель Z3 (значения параметров S и выходов выше)
    F := F ∧ ensures(C)[параметры ↦ σ, result ↦ выход_n] ∧ ограничения типа результата
отображение:  то же поэлементно для i < L (L = длина over, ≤ K), выход — список длины L
свёртка:      acc₀ = init; для i < L: обязательство на шаге, acc_{i+1} из ensures(C); выход = acc_L
запись:       поля выхода = источникам; обязательство — ограничения типа записи
индекс:       доступ по индексу в любом источнике (order.lines[0]) даёт обязательство 0 ≤ индекс < длина
П5 (считается, не блокирует): доказать F ⇒ ensures(S)[result ↦ источник результата]
```

Для каждой операции каждого ребёнка проверяется ещё непустота:

* `requires` выполнимо;
* `requires ∧ ensures` выполнимо хотя бы при одном результате.

Если нет — «условия противоречат друг другу», с минимальным противоречивым набором строк (unsat
core Z3). Противоречие называется в отчёте первым: при нём обязательства ниже бессмысленны.

**Как это записано** (`check.contract`, 28.09.2026). Выход узла схемы — переменная: вызов и
свёртка — типа результата, отображение — списка, запись — типа записи; накопители свёртки —
`n__accI`. Запись даёт равенства полей по скалярным путям: обязательные поля, вложенные записи,
списки — длина и элементы до K. Подстановка `[параметры ↦ σ]` идёт по словам текста условия,
переменные кванторов переименовываются.

**Неполные факты.** Необязательное поле, словарь и составной литерал равенствами не выражаются.
Недостающий факт может дать решателю ложный контрпример, то есть ложный FAIL. Поэтому их пути
собираются отдельно, и опровержение, чей контрпример задевает такой путь, даёт `unknown`, а не
`fail` — тот же принцип, что ERROR ≠ FAIL.

**Контрпример** — значения всех символов модели, и цели, и фактов: цель обязательства записана
через выходы схемы (`n2__acc1.currency == n1[1].currency`), а значения параметров операции есть
только в фактах. В доказательство и отчёт идут пути параметров операции S.

**Параметры проверки:** предел ресурсов решателя `z3_rlimit` на обязательство, K = 3,
фиксированное зерно. Предел ресурсов, а не тайм-аут по часам: вердикт не должен зависеть от
скорости машины, а ядро часов не видит (С-6; принцип arch2 — «стохастика только внутри вызова
модели»). Время проверки пишет оболочка.

### П7. Примеры

Для каждой операции каждого ребёнка и каждого её примера, включая примеры пользователя:

1. `in` проходит схемы параметров, `out` — схему результата;
2. `requires` на `in` — истина;
3. `ensures` при `result = out` — истина (вычисление в Python). Для примера `match: subset`
   гарантии на неполном выходе не вычисляются — их проверит Э2 на настоящем результате;
4. число примеров не меньше I15.

**При провале:** пример и условие, которое он нарушил. Если нарушил пример пользователя — это
всегда вина карточки, а не примера.

Примеры операций составных узлов — сквозные: их вычисленное значение проверяется позже, в Э6, на
собранном коде.

### Э1. Статика функции

* ровно одно определение верхнего уровня `def <имя операции>(…)`: имена и порядок параметров,
  аннотации типов и результата — как в карточке;
* импорты только из разрешённых (узел + эффекты), вызовов кода проекта нет;
* запрещённые встроенные — `eval`, `exec`, `compile`, `__import__`, `globals`, `vars`, доступ к
  атрибутам `__*__`, `open` без эффекта `fs.*`;
* **размер — функция, а не константа** (с 28.09.2026, вывод — `REVERSE-PTG-LIMIT-FUNCTION.md` в
  корне рабочей папки):
  * строк кода не больше 2·D_код + S + 10. D_код — решения в коде по таблице radon; S —
    прямолинейные шаги, которых требует договор (`contracts` в project.yaml, в ядро они приходят
    полем `Config.contracts`; у разборщика
    грамматики — символы правых частей, у остальных 0). Строки кода — без документации,
    комментариев и пустых. Основание: на 21 функции листьев lang строк кода = 2,01·D − 3,9,
    R² 0,91, σ 7 строк; запас 10 = −3,9 + 2σ;
  * если договорное число решений D объявлено до кода (`contracts`), решений в коде не больше
    1,5·D + 5: больше — договор занижен или код раздут;
  * прежний предел физических строк `final_max_lines` — только заместитель ёмкости оператора для
    маршрутизации (правило 6), пока ёмкость не измерена (А10);
* цикломатическая сложность каждого блока не больше `max_complexity` (radon) — предел проекта,
  узел может его ужесточить. Ослабить его может только пользователь ручным назначением
  `max_complexity` (§6.6): функции листа не вызывают друг друга, и разбор по многим видам узлов
  дерева иначе не записать (С-5);
* mypy в строгом режиме — на функции вместе со сгенерированными типами.

**При провале:** строка кода и правило.

### Э2. Условия в исполнении

Скрипт генерирует обёртку: проверка `requires` на входе, вызов функции, проверка `ensures` на
выходе. Каждый пример гоняется в песочнице через обёртку; фактический результат сравнивается с
`out`. Равенство структурное; для чисел с плавающей точкой — с допуском 1e-9, если в примере не
указан свой; десятичные — по числу (`20` и `20.00` равны). При `match: subset` словарь сравнивается
по указанным ключам, список — поэлементно при равной длине, `"*"` совпадает с любым значением.
Сбой кода модели при загрузке модуля — провал примера, а не сбой оснастки: модуль грузится лениво,
внутри вызова (стадии отказа, эксп. 11/12).

**Чистота** (решение пользователя 01.10.2026, после П-12 постройки `plan`). Вызов не меняет свой
вход: прогонщик сверяет вход в JSON до вызова и после. Записи программы изменяемы, и лист,
поправивший вход на месте, портит значение, которое схема отдаёт следующему узлу. Результат и
гарантии при этом могут оставаться верными: «нормализация на месте» (`price ← price·qty, qty ← 1`)
проходит и пример, и `ensures` на изменённом входе. Изменённый вход — нарушение стороны `purity`
испытуемой операции с условием «параметры не меняются: <имена>»: провал примера здесь и провал
свойства с входом в Э3. В Э6 сверка идёт на границе собранного узла. Трасса виновного не называет,
поэтому вина — разложение узла, как у гарантии самого узла; сам лист ловят его Э2 и Э3 раньше
сборки. Замеров о том, как часто модели так пишут, в базе нет — правило из разбора, а не из
измерения.

**При провале:** пример, ожидаемое, фактическое, какое условие нарушено.

### Э3. Тесты на свойства

Hypothesis через ту же обёртку: входы из стратегий §4.4, проверяются `ensures`. Настройки:
`derandomize=True`, 200 примеров, 1 с на пример, без базы примеров. Нарушение `requires` самой
испытуемой операции — фильтр (вход отбрасывается), любое другое нарушение — провал с входом и
первым нарушением трассы. Входы-нарушители, найденные при сборке (Э6), добавляются к Э3 этой
функции как обязательные.

**При провале:** минимальный вход-нарушитель, который нашла Hypothesis. Если валидных входов
слишком мало — `unknown` с предложением владельцу карточки уточнить границы в `requires`.

### Э6. Сборка составного узла

Выполняется снизу вверх: узел собирается, когда приняты все его дети — функции финальных детей и
сборки составных.

**codegen пишет:**

* составной узел — пакет: `__init__.py` (операции узла в обёртках условий), `_flows.py` (код схем:
  вызов — вызов, отображение — генератор списка, свёртка — цикл, запись — конструктор),
  `_types.py` (типы, которыми владеет узел; с подчёркиванием, чтобы не столкнуться с узлом по имени
  `types` — такой есть в самом rptg, находка С-14);
* финальный ребёнок — модуль `<имя>.py` с принятыми функциями: заголовок сборки, метка
  `# ── код модели ──` и код модели как есть — номера строк после метки совпадают с ответом, и
  замечания mypy (Э1) ложатся на строки модели; `from __future__` из кода поднимается в заголовок,
  его строка в коде гаснет;
* составной ребёнок — вложенный пакет, собранный раньше;
* финальный вызываемый схемы идёт через свою обёртку прямо в `_flows.py` вызывающего; литерал схемы
  приводится к типу места (десятичное в программе — `decimal.Decimal`, в JSON — строка);
* корень набора — среда `<корень>/_rt.py` (обёртки условий, перевод JSON ↔ значения, сравнение с
  примером), тестовый модуль `tests/test_<цель>.py` и прогонщик `run_tests.py`.

**Прогон в песочнице** (`rptg.build`, 30.09.2026): `python run_tests.py [all|mypy|tests]` из корня
набора пишет рядом `report.json` — его читает проверка:

* `mypy` — `{"errors": [{"line", "message"}]}`, строки — в коде модели;
* `examples` — `[{"op", "index", "ok", "expected", "actual", "violation", "error"}]`;
* `properties` — `[{"op", "ok", "examples", "counterexample", "violation", "too_few"}]`;
* `violation` — первое нарушение трассы обёрток `{"op": "узел:операция", "side", "cond", "why"}`.

Сбой самой оснастки — отчёта нет и код 2: это `unknown` (ERROR ≠ FAIL), а не провал функции.
Мало годных входов у свойства — `too_few`, тоже `unknown`.

**Проверки узла:**

* примеры и свойства всех операций узла — на собранном коде, с включёнными обёртками всех детей;
* сверка разбора кода с планом: импорты функций — по белым спискам; сгенерированные схемы вызывают
  ровно то, что в разложении. Это страховка: по построению так и должно быть.

**Корень** дополнительно проходит:

* сквозные примеры пользователя;
* пробный запуск: импорт пакета и, если объявлена точка входа командной строки, запуск на примере.

**Распределение вины.** Обёртки пишут трассу; первое нарушенное условие в ней указывает виновного:

| первое нарушение в трассе | чья вина | кто чинит |
|---|---|---|
| требование ребёнка на входе | схема узла | конструктор узла. П4 здесь не доказал: длина больше K или `unknown` |
| гарантия ребёнка на выходе | ребёнок | финальный ребёнок — исполнитель функции, найденный вход становится обязательным в Э3; составной ребёнок — его конструктор |
| гарантия самого узла, дети чисты | разложение слабее карточки (дыра П5) | конструктор узла |
| результат ≠ `out`, все условия выполнены | условия слабее примера | конструктор узла; если пример противоречит карточке — подозрение на карточку |

**При провале:** операция, пример, ожидаемое и фактическое, первый узел схемы, где разошлось, и
вывод таблицы выше.

## 6. Маршрутизация {#routing}

### 6.1. Что решает маршрутизация

Когда разложение узла P принято, для каждого его ребёнка X скрипт решает, **до начала работы** и с
записью в журнал:

1. **вид X** — составной или финальный (§6.2);
2. **класс работы** — для разложения X или для каждой его функции (§6.3);
3. **оператора** — по ручному назначению, таблице компетенций или априорной оценке (§6.4–§6.6).

Корень всегда составной, его раскладывает архитектор.

**Кто делает рёбра:**

* рёбра внутри X — схемы потоков и `uses` его детей — делает оператор, которому назначено
  разложение X;
* рёбра X с братьями делает оператор, раскладывавший родителя;
* исполнитель рёбер не делает.

**Чего маршрутизация не делает.** Она не спрашивает модель «насколько это сложно?»: такой ответ —
SOFT (D1). И не вешает на модели скалярный «рейтинг качества» (F18, F19). Решают правила, измерения
и человек.

### 6.2. Вид узла: сначала целиком

Декомпозиция не повышает качество сама по себе. Она нужна там, где целое не помещается или не
далось (F28, LIFE-9, experiment14 G2 = 0, SWE1). Поэтому по умолчанию узел **финальный**, а
составным становится по необходимости. Правила применяются по порядку, срабатывает первое:

| № | правило | вид |
|---|---|---|
| 1 | X — корень | составной |
| 2 | уровень X = `max_depth` | финальный (I8 гарантирует, что это возможно) |
| 3 | `X.uses` не пуст | составной — финальному вызывать некого |
| 4 | операций больше `final_max_ops` | составной |
| 5 | ручное назначение `kind` | как назначено |
| 6 | `est_lines` > `final_max_lines` × число операций | составной — в функции допустимого размера узел не помещается |
| 7 | иначе | **финальный** |

Правила 1–4 — следствия инвариантов, ручное назначение их не отменяет.

Если функция финального узла не далась всей лестнице исполнителей, узел **повышается** до
составного (§7.4). Это второй путь к декомпозиции — по факту провала, а не по прогнозу.

Оценку размера `est_lines` даёт автор карточки. Это SOFT-вход (допущение А6). Правила используют
её только для двух вещей: решить «помещается ли в функции» и не пустить разложение по кругу (I11).
Фактический размер функций проверяет Э1.

**Куда идёт правило 6** (28.09.2026). Размер функции предсказуем из её договора: строк кода ≈
2·D + S, где D — решения, S — прямолинейные шаги (Э1). Когда договорное D объявляется до кода,
правило 6 должно сравнивать 2·D + S не с константой `final_max_lines`, а с ёмкостью оператора —
размером, который модель ещё пишет. Ёмкость не измерена (А10), поэтому пока правило 6 работает на
`est_lines` и константе. На `lang` константа 60 вынудила одну лишнюю раскладку (`strategy`) —
против F28 и LIFE-9.

### 6.3. Класс работы

Класс — это то, по чему измеряется успех операторов. Он определяется скриптом по карточке, без
модели:

| роль | класс |
|---|---|
| архитектор | `map` — карта и разложение корня |
| конструктор | `design` — разложение узла уровня ≥ 2 |
| исполнитель | род функции, по первому сработавшему признаку: |

| род функции | признак в карточке операции |
|---|---|
| `io` | объявлены эффекты: `fs.*`, `stdout`, `clock`, `random` |
| `compute` | в `ensures` есть арифметика над числами: `+`, `−`, `*`, `/`, `%` |
| `search` | в условиях есть кванторы или агрегаты: `forall`, `exists`, `sum`, `count` |
| `text` | строковые параметры или результат и строковые действия: `len` строки, `startswith`, `in {…}` |
| `transform` | остальное: перекладка полей записей и списков |

Пять родов — **допущение А2**. Нужны ли они, решает гейт G0 при калибровке (§6.4). Образец —
experiment14: там четыре рода шагов дали три разных победителя из шести моделей, и маршрут по роду
решил 0,43 задач против 0,05 у лучшей одиночной.

### 6.4. Таблица компетенций

**Как строится.** Командой `rptg models calibrate` на эталонном наборе. Это одинаковые задачи для
всех операторов: карточки функций со скрытыми тестами, по 12 на род. Набор делится на две половины:

* на **подборе** выбирается маршрут;
* на **проверке** он подтверждается — как в experiment14.

Сравнение только при равной выборке: каждый оператор решает все задачи набора.

**Клетка таблицы:** оператор × класс → доля успеха на подборе и на проверке, объём выборки, цена на
успех. Цена на успех считается по фактическим токенам: многословие оператора входит в неё (F25).
Клетка с выборкой меньше `n_min` (по умолчанию 10) помечается «мало данных».

**Гейт G0.** Маршрут по роду включается, только если у разных родов разные победители. Иначе все
функции маршрутизируются по общей доле успеха роли. Так в K1: пул не был дифференцирован, и выбор
шёл по измеренной точности, а не по «специальности».

**Точные правила калибровки** (постройка `bench`, 01.10.2026; REVERSE-PTG-BENCH.md §2):

* **Раздел** — по роду, внутри рода — по возрастанию хэша имени задачи, равные хэши — по имени;
  чётные места общего списка — подбор, нечётные — проверка. Каждый род делится поровну, ±1 (К-8,
  утверждено пользователем 02.10.2026): в experiment14 каждая задача несла все роды шагов, и раздел
  задач делил их поровну, а у задачи rptg один род, и общий порядок по хэшу на 3 родах по 12 задач
  давал подбор/проверку 3/9, 8/4, 7/5. Раздел фиксирован до прогона и от исходов не зависит; в
  experiment14 — по зерну, в ядре случайности нет.
* **Победитель рода** — наибольшая доля успеха **на подборе** (нет задач подбора — доля 0), при
  равенстве — дешевле на успех, затем по имени. Проверка в выбор не входит: в experiment14 таблица
  «обучается на train и применяется к test», иначе это выбор задним числом.
* **Цена на успех** — все расходы клетки, включая неудачные попытки, на число успехов подбора и
  проверки (arch2: c = total_cost / solved). Успехов нет — у arch2 бесконечность, запись `Decimal`
  её не выражает: расходы всех попыток. Доля успеха такой клетки — 0, в маршрут она не попадает.
* **Десятичные** — с масштабом, как у модуля `decimal`: сумма — в масштабе самой длинной записи,
  точное частное — в нём или в стольких знаках, сколько нужно, не больше max(масштаб, 18), иначе
  округление половины к чётному. Цены сравниваются по числу («0.0020» = «0.002»).
* **Без G0** клетки оператора складываются по родам: выборка — подбор и проверка, «мало данных» —
  сумма меньше `n_min`; цена — взвешенная всеми успехами клеток.
* **Итоги:** задача вне плана не считается; повтор пары (задача, оператор) — последний, перезапуск
  заменяет прежний итог, иначе выборка перестала бы быть равной.

**Выбор оператора для задачи класса c роли r:**

```
если есть ручное назначение             → оно
иначе если клетка c есть и не «мало данных» →
    самый дешёвый на успех оператор лестницы r, у которого
    доля успеха на подборе ≥ target (0,8) и на проверке ≥ target − 0,1
иначе                                    → ступень лестницы по априорной оценке (§6.5)
```

**В MVP калибруются исполнители.** Разложения калибруются в v0.1: для них нужен набор эталонных
замыслов с примерами пользователя (замер 3 в [BASIS §4](BASIS.md)). До этого конструктор и
архитектор назначаются руками и лестницей, и по умолчанию это сильные модели. LIFE-9: планировщик
1,5B выбирает нужную величину в 22 % случаев.

### 6.5. Холодный старт: априорная оценка

Пока клетки таблицы нет, стартовую ступень выбирает оценка по карточке. **Это допущение А1**: веса
не измерены, у формулы одна задача — дать разумный старт и быть видимой.

**Признаки операции o** (нормировка f = min(1, значение / насыщение)):

| признак | как считается | насыщение |
|---|---|---|
| `types` | узлов схем во входах и результате: каждый объект, список и скаляр — один узел | 40 |
| `cond` | узлов разбора CL во всех `requires` и `ensures` (§4.5) | 60 |
| `quant` | кванторов и агрегатов | 4 |
| `nonlin` | нелинейных операций | 2 |
| `effects` | число эффектов | 3 |
| `size` | `est_lines` узла / число операций | `final_max_lines` |
| `text` | описание операции и назначение узла, в токенах (≈ символов / 4) | 300 |

**Признаки узла X** (для разложения):

* `types`, `cond`, `quant` суммируются по операциям, `effects` — объединение;
* `ops` = (число операций − 1) / 7;
* `uses` — размер `X.uses`, насыщение 6;
* `size` — `est_lines`, насыщение 1000;
* насыщения: `types` 80, `cond` 120, `quant` 6, `text` 600.

```
S_исп(o)  = 100 · (3·cond + 2·quant + 1·nonlin + 2·types + 1·effects + 3·size + 1·text) / 13
S_раз(X)  = 100 · (3·ops + 2·types + 2·cond + 1·quant + 1·effects + 2·uses + 4·size + 2·text) / 17
```

**Ступень** — число границ роли, не превышающих оценку, плюс 1. Например, исполнители
`[gguf, mini, gemini, opus]` с границами `[30, 55, 75]`: оценка 12 → `gguf`, 60 → `gemini`.

Что делает журнал с этой формулой (допущение А1): при калибровке видно, связана ли оценка с успехом
при равной выборке. Если нет — формула убирается, а старт идёт с первой ступени.

### 6.6. Ручные назначения

Раздел `overrides` в `project.yaml`:

```yaml
overrides:
  "level:2..3":        {designer: grok}                 # уровни 2–3 раскладывает Grok
  "app.billing.**":    {implementer: gemini}            # весь billing с поддеревом
  "app.tax.compute":   {kind: final, implementer: opus}
  "app.ui.**":         {designer: opus, approve: true}  # своё утверждение на поддерево
  "app.report.*":      {start_rung: 2, max_rung: 3}     # только прямые дети report
```

**Маски:**

* `*` — ровно один сегмент пути;
* `**` — сам узел и всё его поддерево;
* `level:a..b` — уровни с a по b.

**Ключи:**

* `kind` — `final` или `composite`;
* `designer`, `implementer` — оператор. Он обязан стоять в лестнице роли; эскалация идёт вверх от
  него;
* `start_rung`, `max_rung` — номер ступени или имя оператора;
* `approve` — утверждение пользователем каждого разложения в поддереве;
* `steps` — `combined` или `split` (§8.2);
* `est_lines` — замена оценки автора карточки;
* `max_complexity` — ослабить предел сложности блока Э1 для узла. Нужен разбору по многим видам
  узлов дерева: функции листа не вызывают друг друга (С-5). Ослабить может только пользователь;
* `max_lines` — явный ручной предел физических строк сверх функции размера Э1. С 28.09.2026 размер
  задаёт функция договора, и ослаблять предел строк вручную больше не нужно; назначение осталось
  для листьев, чей договор ещё не размечен.

**Старшинство:** точный путь > маска с большим числом буквальных сегментов > уровень > таблица
компетенций > априорная оценка. При равной точности побеждает позднее в файле.

Изменённое назначение действует на ещё не начатые задачи. Принятое не переделывается без команды
пользователя.

### 6.7. Адаптация внутри проекта

**Допущение А5, по умолчанию выключено** (`routing.adapt: false`). Если включить: когда у одного
родителя две задачи одного класса уже потребовали ступени выше стартовой, оставшиеся задачи этого
класса у того же родителя стартуют со старшей из достигнутых ступеней. Источник назначения
записывается как «адаптация». Вниз адаптация не сдвигает.

### 6.8. Журнал исходов

Каждая завершённая задача дописывает строку в `outcomes.jsonl`:

```json
{"task": "function", "subject": "app.billing.lines:line_total", "role": "implementer",
 "class": "compute", "operator": "gguf/qwen2.5-coder-7b-q4/p3/implementer",
 "prior_score": 15, "decided_by": "prior", "explore": false,
 "start_rung": "gguf", "final_rung": "gguf", "attempts": 2, "form_retries": 0,
 "result": "accepted", "tokens": {"in": 2310, "out": 184}, "finish_reason": ["stop", "stop"],
 "cost": 0.0, "seconds": 41}
```

**Чему журнал рабочих прогонов верить нельзя.** На старшие ступени доходят только задачи, уже
проваленные ниже, — это смещение отбора. Поэтому по журналу операторы **не сравниваются**.

Журнал нужен для трёх вещей:

* наблюдать дрейф;
* проверять допущения А3–А6;
* копить несмещённую выборку, если включена **разведка**: `routing.explore` — доля задач (по
  умолчанию 0), которым ступень назначается случайно и помечается `explore: true`.

Сравнивает операторов только калибровка (§6.4).

## 7. Состояния, эскалация, владение {#escalation}

### 7.1. Фазы проекта

```
NEW → MAP → MAP_CHECK → MAP_REVIEW ──(утверждено)──► DESIGN → BUILD → E2E → DONE
       ▲        │            │
       └────────┘            └──(отказ с комментарием)──► MAP
любая фаза → PAUSED(бюджет | пользователь | утверждение поддерева | остановка) → та же фаза
```

* **MAP** — архитектор пишет карту `map.md`, карточку корня (с примерами пользователя) и
  разложение корня.
* **DESIGN** — очередь составных узлов без принятого разложения: по уровням сверху вниз, внутри
  уровня — по пути. Принятое разложение → маршрутизация детей (§6) → составные дети встают в
  очередь.
* **BUILD** — функции финальных узлов в любом порядке, друг от друга они не зависят. Сборки
  составных узлов — снизу вверх.
* **E2E** — Э6 корня с примерами пользователя и пробным запуском.

В MVP фазы идут подряд: BUILD начинается, когда разложено всё дерево и удалены мёртвые операции.
Подозрение снизу может вернуть поддерево в разложение. Фаза проекта при этом не меняется — правду
показывают состояния элементов.

**Утверждения.** Разложение корня утверждается всегда. Разложения в поддеревьях с `approve: true` —
тоже, остальное дерево тем временем продолжает работу. Изменение утверждённого разложения требует
нового утверждения, и окно показывает разницу.

### 7.2. Состояние элемента

Элементы — разложение составного узла, функция финального узла, сборка составного узла.

```
planned → writing → checking → accepted
             ▲          │  └→ approval ─► accepted                       (разложение под утверждением, §7.1)
             │          ├→ form_retry ─► writing                       (нарушение формы, §7.3)
             │          └→ rejected → repairing ─► checking            (есть попытка на ступени)
             │                     └→ escalated(ступень+1) ─► writing  (попытки на ступени кончились)
             │                     └→ promoted                         (функция: лестница кончилась, §7.4)
             │                     └→ card_suspect → владельцу         (лестница кончилась или раннее подозрение)
любое → stale → checking   (изменилось то, от чего элемент зависит)
```

### 7.3. Эскалация: политика — данные на языке arch2

**Политика элемента** — что делать после каждой проверки. Она записывается **генотипом на языке
комплексов arch2** (`trace-probe/arch2/SPEC.md` §1.1) и в код не зашивается. Язык в проекте уже
есть, измерен и реализован:

* восемь узлов;
* статический валидатор;
* исполнитель с гарантией бюджета и полной трассой;
* 152 контрольных случая.

rptg берёт семь узлов. Восьмой, ASSEMBLE, не нужен: шаги задачи в rptg задаёт само разложение.

| узел | смысл в rptg |
|---|---|
| `CALL(оператор, формулировка, с отчётом)` | один вызов модели. Оператор — назначенный (§6), конкретный или «следующая ступень» |
| `CHECK` | все требуемые проверки элемента (§5) |
| `SEQ[…]` | последовательно, состояние идёт вперёд |
| `PAR[…]` | ветви от одного состояния; побеждает первая, прошедшая доверенные проверки, остальные не запускаются |
| `SWITCH(наблюдаемая, {значение → узел}, default)` | выбор по механически наблюдаемой величине; `default` обязателен |
| `BUDGET(n, узел)` | потолок токенов на поддерево |
| `STOP(причина)` | конец: принят, подозрение, повышение, пауза |

**Циклов нет, и это не упущение.** arch2 исключил их сознательно: с циклом нельзя статически
оценить верхнюю стоимость, и гарантия `BUDGET` рушится. Поэтому лестница записывается развёрнуто —
`SEQ` по ступеням.

Исполнитель политики детерминирован: при тех же ответах моделей — та же последовательность узлов.
Стохастика есть только внутри `CALL`.

**Наблюдаемые — закрытый список:**

* `violation_subtype` — подтип нарушения;
* `same_failure` — то же ли нарушение, что в прошлый раз (классификатор эксп. 12);
* `attempts_used`;
* `work_class`;
* `tokens_bucket`.

**Подтипы нарушений** — ось, по которой в опытах различалась цена ремонта. Данные arch2
(REPORT §2.3): малые модели, повтор после отказа.

| подтип | нарушения rptg | доля решённых повтором | токенов на решённую |
|---|---|---|---|
| `form` | П1; код не разбирается (Э1) | 0,59 | 190 |
| `contract` | П2, П3; сигнатура и импорты (Э1) | отдельно не измерено | — |
| `semantic` | П5, П7 | 0,31 | 363 |
| `dependency` | П4 | 0,13 | 1576 |
| `value` | Э2, Э3, Э6 | 0,10 | 2051 |
| `other` | остальное | 0,08 | 2455 |

Цена различается в 13 раз. Поэтому выбор по подтипу оправдан, а на дорогих подтипах повтор той же
моделью — нет.

**Политика по умолчанию** выведена из измеренного. Исполнителю она выглядит так:

```
BUDGET(бюджет задачи,
 SEQ
  CALL назначенный [основная]                  ← один вызов правильным оператором
  CHECK
  SWITCH violation_subtype
    none                     → STOP(принят)
    form                     → SEQ[ CALL тот же [другая формулировка], CHECK,
                                    SWITCH violation_subtype { none → STOP(принят); default → ступень 2 } ]
    contract, semantic       → SEQ[ CALL тот же [основная + отчёт], CHECK,
                                    SWITCH violation_subtype { none → STOP(принят); default → ступень 2 } ]
    dependency, value, other → ступень 2

 ступень k = SEQ[ CALL ступень k [основная + отчёт], CHECK,
                  SWITCH same_failure
                    SAME    → STOP(подозрение на карточку)
                    default → SWITCH violation_subtype { none → STOP(принят); default → ступень k+1 } ]
 после последней ступени → STOP(повышение узла; на max_depth — подозрение на карточку))
```

`repair.per_rung` и `repair.form_retries` задают число таких повторов в генотипе.

**Исполнение — по событиям** (постройка `plan`, 01.10.2026). arch2 исполняет генотип одним
прогоном и сам зовёт модели; ядро rptg чисто, поэтому генотип исполняется шагами: позиция элемента —
путь узла в записи arch2 (`root/seq[i]/case[v]/default/par[i]/budget`) с режимом — `reopen`
(начать сначала, первому вызову приложить отчёт), `resume` (продолжить с ветви, куда вела бы
default), `extra` (лишний круг на верхней ступени), `recheck` (перепроверка ждёт прогонов),
`user:<причина>` (ждёт пользователя). Ответ приходит к той же позиции, исполнение идёт от
следующего узла до первого CALL или STOP. Нарушение формы на любой ступени чинится той же моделью
другой формулировкой и в подозрение не ведёт; «провалиться дальше» в дереве без циклов — ветвь
`default: CHECK`. **Рамка BUDGET** — расход элемента: позиция ищется по расходу до события, дальше
— по расходу после; вход в исчерпанную рамку и приход к CALL под ней — STOP(budget). Рамка
ограничивает следующие вызовы, а не полученный ответ: годный ответ, перешедший рамку, принимается.
**STOP до первого вызова** — пауза всего проекта с причиной (решение пользователя 01.10.2026). Выбор
действия ничего не пишет, поэтому остановка, к которой исполнение приходит раньше вызова (например,
`PAR[STOP(причина), …]`), в элемент не записывается: `plan_next` отдаёт паузу и держит голову
очереди, пока политику не поменяют. Для политик ролей так и задумано: «роль выключена» останавливает
проект, а не отдельный узел.

| решение | основание |
|---|---|
| начинать с одного вызова назначенного оператора | arch2 E1, живой прогон: «одна попытка правильной моделью» дешевле эталонов в 2,06–2,21 раза на решённую задачу, CI не задевает единицу |
| форма → та же модель, другая формулировка | эксп. 12: 93,0 % против 73,9 %, p = 5,9·10⁻⁵; эксп. 11: смена модели на таких отказах хуже (54 %) |
| дешёвые подтипы → одна починка той же моделью с отчётом | эксп. 12: та же модель с отчётом лучше смены на равную (−8,8 п.п., p = 0,0042); эксп. 11: отчёт поднимает успех с 16,1 % до 22,0 % |
| дорогие подтипы → сразу следующая ступень | arch2 E4: повтор одной моделью даёт 1,6 независимой попытки из 4; четвёртая попытка в 7,9 раза дороже первой |
| тот же провал на другой ступени → подозрение на карточку | F11: ложный отказ по неверной спецификации одинаков у всех моделей. Но бывает и общая слепая зона (F23) — **допущение А4** |
| следующая ступень — более сильный оператор | **допущение А3**: переход на более сильную модель в опытах не измерялся |
| всё поддерево под BUDGET | I-11, arch2: без потолка смерть линии механически не наступает |

**Повтор** — ответ совпал по хэшу с прежним — попыткой не считается: исполнитель меняет зерно или
температуру. Эксп. 10: при фиксированном зерне 89,8 % повторов побайтово одинаковы.

**Другие политики** — тоже генотипы, их ставят на роль в `project.yaml` (`policies`). Самая заметная
альтернатива — портфель `PAR[CALL оператор A, CALL оператор B, …]`. arch2 измерил её при равном
бюджете:

* разнородное размещение (4 модели по одному вызову) решает на 9,88 п.п. больше однородного
  (1 модель × 4). CI [+5,79; +14,18], на 15 наборах из 15;
* но от «лучшей модели под класс», выбранной задним числом, портфель статистически неотличим:
  +0,050, CI [−0,100; +0,200].

В rptg роль такой модели играет таблица компетенций. Поэтому портфель стоит ставить там, где
таблица не называет явного победителя.

**Как выбирается политика.** `bench` прогоняет политики-кандидаты **по журналу исходов, без новых
токенов** — повтором, как E0 в arch2. Лучшие подтверждаются вживую на отложенных задачах.

* По arch2 E1 отбор по записанному переносит на живой прогон **ранжирование** (знак сохранился у 5
  из 5), но не абсолютные числа.
* Эволюция политик — исследование, а не MVP: в arch2 отбор с ASSEMBLE не обошёл жёсткий алгоритм
  (V3 — провал).

**Добавка к подсказке окупается, только если** ln(q₁/q₀) > ln(c₁/c₀): рост доли успеха обязан
перекрыть рост цены. Это критерий arch2 §2.4, он воспроизвёл знак вердикта на 9 плечах из 9.
Структурный контекст удлинял подсказку на 32 % и поднимал решаемость лишь на 11 % — не окупился.
Поэтому отчёт о нарушении короткий (§8.4), а его окупаемость журнал проверяет тем же критерием.

**Починка** — та же задача плюс отчёт о нарушениях (§8.4). **Прежний ответ целиком не
показывается** (CONTEXT_MODEL §4.1, открытый вопрос OQ-CTX-1). Отчёт сам цитирует нарушившее место.
Модель не видит чужих попыток и чужих карточек сверх контекста задачи.

**Разложения** идут по той же политике с ролью конструктора: лестница конструкторов, в конце —
подозрение на карточку узла. Карта и разложение корня — политика архитектора, в конце — вопрос
пользователю.

### 7.4. Повышение листа

Если функция финального узла X не далась всей лестнице исполнителей:

* **карточка X не меняется** — договор тот же, меняется только способ его выполнить;
* X становится составным (источник вида — «повышение») и получает конструктора;
* **принятые функции X не пропадают:** если конструктор создаст финального ребёнка с той же
  карточкой операции, код и доказательства переиспользуются по хэшу (§10);
* на `max_depth` повышение невозможно → подозрение на карточку;
* событие записывается в журнал: целиком не далось, и это главный сигнал для А6 и калибровки.

### 7.5. Подозрение на карточку

**Владелец карточки** — тот, чьё разложение её создало. Владелец карточки корня — архитектор, под
утверждением пользователя.

Владелец получает:

* карточку;
* все отчёты о нарушениях снизу;
* сильнейшие контрпримеры;
* возражение модели снизу, если оно было. В ответе конструктора и исполнителя есть необязательное
  поле «возражение»: оно ничего не решает, только прикладывается к подозрению.

Он обязан сделать одно из трёх:

* **выпустить ревизию своего разложения** — ослабить гарантию, усилить требование, исправить
  пример, разделить узел, поменять схему или состав братьев. Ревизия проходит все проверки
  разложения, зависимое устаревает (§7.7). Если нужная правка задевает его собственную карточку,
  подозрение уходит уровнем выше;
* **пересобрать разложение заново** — новая версия, старая не удаляется, принятое переиспользуется
  по хэшу (DECOMPOSITION_MODEL §6.2). Окно показывает, сколько уже стоили починки поддерева и
  сколько стоит пересборка: локальный ремонт не всегда дешевле (F46, F47);
* **оставить карточку** с письменным обоснованием — тогда лестница снизу продолжается с места, где
  её прервало раннее подозрение. Если лестница уже была исчерпана — ещё один круг на верхней
  ступени, при новом провале вопрос уходит пользователю.

Пример пользователя не может быть «неверным» в глазах скрипта. Если карточка с ним спорит, ревизия
обязательна.

**Когда ревизия вступает в силу** (постройка `plan`, 01.10.2026). По ответу владельца, прошедшему
проверки, — а не по приёмке: разложение корня принимается на утверждении, когда прежней версии в
состоянии уже нет. Карточка подозреваемого не изменилась — «оставить»: лестница продолжается, круг
подозрения считается (`round`); изменилась — подозреваемый начинается заново на новой карточке
(§7.7). Отказ пользователя от разложения снимает и элементы его поддерева: они принадлежали
отвергнутой версии, следующая разводит детей заново, код функций перепроверяется без модели.

### 7.6. Мёртвые операции

Когда разложено всё дерево, скрипт находит операции, недостижимые от операций корня (I10). Он
удаляет их каскадом:

* дети, которые вызывались только из удалённых схем;
* типы, которые использовались только там.

Скрипт пишет ревизию «удалено: не используется» и показывает список пользователю. Удаление ничего
не ломает: эти операции никто не вызывает.

### 7.7. Устаревание

| что изменилось | что устаревает |
|---|---|
| карточка узла X | схемы, вызывающие X (у родителя и у узлов, где X в `uses`): П3, П4; разложение X против нового интерфейса; функции X, если он финальный: Э1–Э3; сборки X и всех предков |
| тип T | все карточки и разложения, где встречается T, — дальше как выше |
| разложение X | карточки детей X получают новые хэши — дальше как выше; сборки X и предков |
| функция | её Э1–Э3; сборки её узла и предков |
| утверждённое разложение | нужно новое утверждение |

Устаревшее сначала **перепроверяется**. Если проверки проходят на новых хэшах, элемент принят снова
без единого вызова модели (F37, F38: устаревание ≠ ошибка). Модели нужны только там, где проверка
упала.

Устаревшие доказательства не удаляются: они перестают совпадать по хэшу и перестают засчитываться.
Независимые ветви не устаревают никогда (F35).

Перепроверять можно только сохранённое — карту, разложение, код. **Непринятый элемент
изменившегося узла без сохранённой версии начинается заново** на новой карточке: без назначения
(новая карточка — новая прикидка), позиции, отчётов и хэшей ответов — прежние провалы и повторы
относились к прежней задаче. **Ждущее утверждения не перепроверяется**: его только что проверили, а
принимает его пользователь (иначе перепроверка обходила бы утверждение). Карта перепроверяется по
просьбе пользователя после «не знаю» (ERROR ≠ FAIL) — тем же путём.

### 7.8. Остановки

Остановка — нормальное состояние, а не авария (REPAIR_MODEL §7). Каждая пишется в журнал с
причиной:

| условие | признак | исход |
|---|---|---|
| колебание ревизий | карточка или разложение вернулись к версии, бывшей две ревизии назад | `PAUSED`, вопрос пользователю с обеими версиями |
| повтор состояния | после круга подозрения — тот же набор нарушений на тех же хэшах | `PAUSED`, вопрос пользователю |
| бюджет | исчерпан бюджет проекта, фазы, роли или задачи | `PAUSED(бюджет)` |
| лестница у корня исчерпана | §7.3 | вопрос пользователю |

## 8. Задачи для моделей {#tasks}

### 8.1. Виды задач

| задача | роль | получает | возвращает (строгая схема) | проверки |
|---|---|---|---|---|
| **К карта** | архитектор | замысел, приёмочные примеры, правила метода, схема формата | `map.md` с разделами `{#id}` — по разделу на будущий узел уровня 2, с эскизом его устройства; типы корня; карточку корня с `est_lines`. Примеры пользователя входят в неё как есть | П1, П4 (непустота), П7 |
| **Р разложение узла X** | архитектор для корня, конструктор для остальных | карточку X; раздел карты своей ветви; путь от корня — имя и назначение каждого предка одной строкой; интерфейсы узлов из `X.uses`, только операции; видимые типы; пределы проекта | карточки детей с `est_lines`, новые типы, схемы потоков всех операций X, необязательное возражение | П1 П2 П3 П4 П7 (+П5) |
| **Ф функция** | исполнитель | карточку одной операции; назначение узла одной строкой; классы используемых типов; разрешённые импорты и эффекты | один блок кода с одной функцией, необязательное возражение | Э1 Э2 Э3 |
| **повтор формы** | тот же оператор | задачу в другой формулировке + жёсткое требование формы | как задача | как задача |
| **починка** | тот же оператор | задачу + отчёт о нарушениях; **без прежнего ответа целиком** | как задача | как задача |
| **ревизия** | владелец | §7.5 | ревизию своего разложения, пересборку или обоснование | проверки этого разложения |

Правило контекста — **только перечисленное.** Исполнитель не видит дерева, конструктор не видит
чужих поддеревьев (F35: соседние ветви не нужны и только добавляют цену и дрейф).

С 29.09.2026 (`rptg.talk`) правило — гарантия операции, а не пожелание. Факты задачи — разделы
из закрытого списка ключей, и `talk.context` гарантирует:
* у карты — только замысел и примеры;
* у функции — только карточка операции, назначение, типы, импорты и пределы;
* текущее разложение и отчёты снизу — только у ревизии;
* отчёт есть тогда и только тогда, когда он есть в задаче.

Ключа для прежнего ответа среди разделов нет вовсе (F1). Контекст не режется: молчаливое
обрезание порождает ошибки, неотличимые от ошибок модели (CONTEXT_MODEL §6). Размер подсказки
план проверяет до вызова (§11).

**Повтор формы** меняет только указание задачи и добавляет строку о форме; факты те же
(experiment13). **Починка** ставит отчёт первым разделом, сразу после указания задачи, и за ним
строки «исправь ровно это, прежнего ответа не будет, карточку и интерфейсы uses не трогай».
Отчёт идёт первым, потому что у моделей 1–2B полнота нахождения записи падает с её позицией
монотонно: 0,609 на позиции 0 против 0,214 на позиции 17, без U-образного провала (K1, «контора
Кана»). Перенесено направление, число на подсказках rptg не мерено. Префикс у повтора и починки
тот же, что у первой попытки, поэтому кэш поставщика держится.

У каждой подсказки есть **версия**. Она входит в идентичность оператора: изменил подсказку —
получил другого оператора, чья калибровка начинается заново (MODEL_INTERFACE §2). Тексты
подсказок — данные разложения `rptg.talk` (`texts_p1`): они входят в его хэш, и правка текста
снимает утверждение. Язык указаний — английский, данные узлов — на языке пользователя.

### 8.2. Пошаговое разложение для слабых моделей

`steps` в профиле оператора или в назначении: `combined` (по умолчанию) или `split` (набор `local` в
[ARCHITECTURE §8](ARCHITECTURE.md#cli)).

* **combined** — один ответ со всем: дети, типы, схемы.
* **split** — три шага, каждый со своей схемой ответа и своими проверками:

  | шаг | что пишет модель | проверки после шага |
  |---|---|---|
  | Р1 состав | дети: путь, назначение, `uses`, `est_lines`; имена и схемы новых типов | П1; из П2 — I1–I3, I8, I9, I11 |
  | Р2 интерфейсы | операции детей: параметры, результат, условия, примеры | П1, П4 (непустота), П7 |
  | Р3 потоки | схемы всех операций X | П2 целиком, П3, П4 |

  Если Р3 не проходит и после своей починки, работа возвращается к Р2 с отчётом. Это считается
  одной починкой всего разложения.

Шаги можно отдать разным операторам: `steps: {mode: split, flows: gemini}`. Например, договоры —
сильной модели, связывание — дешёвой, ведь схемы проверяются точнее всего.

Пошаговый режим не делает малую модель хорошим конструктором: LIFE-9 предупреждает, что малые
планировщики промахиваются. Он лишь даёт шанс модели среднего размера. Годится ли он, покажет
калибровка разложений (v0.1).

**В MVP шагов нет** (29.09.2026). Для них нет трёх вещей:
* типов ответа шага;
* места под черновик принятых шагов в состоянии — у `Element` его нет, а `NodeCard.ops` требует
  хотя бы одной операции, так что черновик Р1 не пройдёт как `Design`;
* поддержки проверкой: П1 пишет «пошаговое разложение проверкой ещё не поддержано».

`talk` строит подсказку шага как подсказку разложения целиком. `plan` не должен ставить шаговых
задач, пока шаги не поддержаны от начала до конца.

**Почему шаги стоят первыми в очереди после MVP.** В линии роя (theory_emergent_swarm, «контора
Кана») сочетание моделей превзошло лучшую одиночную ровно один раз — в E0, где разные модели
давали разные **части одного ответа**: 0,870 против оракула 0,840. Ни голосование по целому (G1),
ни сборка по кускам входа (K1) этого не повторили: пул сверх лучшей одиночной даёт от 0 до
+0,08. Шаги Р1–Р3 разными операторами — как раз части одного ответа.

### 8.3. Ответ у разных поставщиков

Содержание задачи одинаково для любой модели. Различается только способ получить строгий ответ —
его задаёт профиль оператора:

| способ | как |
|---|---|
| `json_schema` | родной структурный вывод поставщика со схемой задачи |
| `tool` | схема задачи — вход единственного инструмента; ответ — аргументы его вызова |
| `grammar` | грамматика llama.cpp из JSON Schema: невалидный JSON модель выдать не может |
| `prompt` | схема в тексте подсказки; ответ — единственный блок `json` |

**Способ профиля — просьба.** Исполняется первый способ из предпочтений, который поставщик умеет
для ответов rptg:

| просьба | предпочтения |
|---|---|
| `json_schema` | `json_schema`, `tool`, `prompt` |
| `tool` | `tool`, `json_schema`, `prompt` |
| `grammar` | `grammar`, `json_schema`, `tool`, `prompt` |
| `prompt` | `prompt` |

| поставщик | умеет |
|---|---|
| `anthropic` | `tool`, `prompt` |
| `openai`, `openrouter`, `openai_compatible` | `json_schema` (без `strict`), `tool`, `prompt` |
| `google` | `json_schema`, `prompt` |
| `llamacpp` | `grammar`, `json_schema`, `prompt` |

`json_schema` у Anthropic нет. Его строгий вывод не вмещает словарей и непрозрачного JSON, а они
есть в каждом ответе rptg (ARCHITECTURE §5.1). У функции способ — `grammar`, если его просит
оператор и поставщик умеет (грамматика одного блока `python`), иначе `prompt`. Исполненный способ
пишется в запрос. Договор ответа объявлен в тексте подсказки при любом способе (experiment14).

**Всегда:**

* сырой ответ сохраняется до разбора;
* ответ проверяет JSON Schema скрипта (П1). Невалидный JSON — нарушение формы, путь §7.3;
* функция — единственный блок `python` у любого поставщика; проверяет Э1.

**Кэш.** Правила метода, схема формата и инструкции роли — стабильный префикс, одинаковый у всех
задач роли и вида при одном способе вывода. Предмет задачи и отчёт идут после него. Так префикс
кэшируется у поставщиков, которые это умеют. Ключ кэша подсказки — digest префикса.

**Схема ответа** в подсказке и у поставщика — та же, по которой проверяет П1: записи закрыты,
непрозрачный Json открыт. Отличается только запись ссылок: `{$ref: "#/$defs/Имя"}` вместо
`{$ref: Имя}` ядра. Контрольный случай `talk` держит это равенство.

### 8.4. Отчёт о нарушениях

Генерируется шаблоном, без модели. Он самодостаточен: модель, которая не видит прежнего ответа,
получает из отчёта нарушившее место, ожидание и контрпример.

```json
{"subject": "design:app.billing", "layer": "P4", "rule": "I13",
 "where": "схема make_invoice, узел n2: свёртка money:add по n1, шаг 1, параметр b",
 "fragment": "{id: n2, fold: money:add, over: n1, init: n0, acc: a, item: b}",
 "expected": "a.currency == b.currency",
 "counterexample": {"len(order.lines)": 2, "order.lines[0].currency": "USD", "order.lines[1].currency": "EUR"},
 "means": "требование вызываемой операции не гарантировано выше по потоку"}
```

Отчёт короткий и точный: модель получает контрпример, а не пересказ. Он одинаков для любой модели.
Это важно для лестницы: следующая ступень получает то же, что и предыдущая.

Место и фрагмент кладёт в доказательство сама проверка, пока предмет у неё под рукой. Отчёт их
только переносит: непринятого разложения в состоянии нет. Слова вида «по стоимостям строк»
шаблон не порождает — это была ошибка примера до 28.09.2026.

## 9. Сквозной пример: дыра в архитектуре находится до кода {#example}

Проект:

* `app` — корень;
* `app.billing` — составной;
* `app.money` — финальный;
* `app.billing.lines` — финальный.

Маршрут — из §6.9.

1. **MAP.** Архитектор (`opus`) раскладывает корень:
   * дети `app.billing` и `app.money` с карточками из §2.6;
   * `app.billing.uses = [app.money]`;
   * схема входной операции `app:invoice` — один вызов `billing:make_invoice`.

   Проверки проходят, пользователь утверждает карту.
2. **Маршрутизация детей корня** — по таблице §6.9.
3. **DESIGN `app.billing`.** Конструктор (`gemini`) возвращает разложение из §2.6. П4 на схеме
   `make_invoice`:
   * **Шаг 0 свёртки проходит.** Накопитель — ноль в валюте первой строки, а `line_total`
     гарантирует валюту своей строки.
   * **Шаг 1 не проходит.** Обязательство `acc₁.currency == n1[1].currency` сводится к
     `order.lines[0].currency == order.lines[1].currency`, а `requires(make_invoice)` ничего не
     говорит о валютах строк.

   Z3 даёт контрпример: две строки, EUR и USD.
4. **Повтора у `gemini` нет.** Провал П4 — подтип `dependency`, дорогой, поэтому политика (§7.3)
   сразу идёт на следующую ступень. Да и не помог бы повтор: карточку `make_invoice` конструктор
   менять не вправе (I17), она принадлежит разложению корня. Никакая схема из доступных операций не
   выводит «все валюты равны».
5. **Ступень 2, `grok`**, упирается в то же обязательство после подстановки
   (`same_failure = SAME`). Два разных оператора подряд — **раннее подозрение** (§7.3): 2 попытки
   вместо 6 по всей лестнице.
6. **Подозрение** уходит владельцу карточки — архитектору. Он выпускает ревизию разложения корня:
   * в `requires` операции `make_invoice` добавлено
     `forall l in order.lines: l.currency == order.lines[0].currency`;
   * это же требование — у `app:invoice`, иначе П4 корня не докажет вызов.

   Примеры пользователя — в одной валюте, П7 проходит. Вариант решения — отдельная операция для
   смешанных валют.
7. Разложение корня изменилось → **повторное утверждение** пользователем, с показом разницы.
8. П4 у `app.billing` проходит. Только теперь `line_total` уходит исполнителю.

Ни одной строки кода ещё не написано, а ошибка проектирования уже найдена и исправлена владельцем —
уровнем выше места, где она проявилась. На уровне 6 было бы то же самое: подозрение поднялось бы к
владельцу карточки на уровне 5.

## 10. Правило приёмки {#acceptance}

H(x) — хэш содержимого x. **Он не зависит от положения в дереве**, поэтому при повышении листа и
пересборке разложения работа переиспользуется.

| x | что входит в H(x) |
|---|---|
| операция | каноническая JSON-запись карточки операции без имени + хэши используемых типов |
| карточка узла | хэши операций, `uses`, эффекты, разрешённые импорты |
| разложение узла X | само разложение (карточки детей, новые типы, схемы) + **карточка X + карточки узлов из `X.uses` + типы, которыми владеют строгие предки X**. Свои типы X лежат в самом разложении. Прототип брал и их, и после приёмки, когда типы X попадают в состояние, хэш менялся (28.09.2026) |
| карта | ответ карты (текст, карточка корня, типы корня) + примеры пользователя |
| функция | код + H(операции) + разрешённые импорты и эффекты её узла |
| сборка узла | H(разложения) + хэши принятых детей (функций и сборок) |

**Правило для любого H: в хэш входит всё, против чего предмет проверялся.** Иначе проверка
устаревает незаметно. В версии 0.3 H(разложения) не включал карточку узла и узлов `uses`: когда
владелец менял карточку, старое доказательство П4 оставалось «текущим» (находка С-9 при описании
rptg собственным методом, design/map.md §7).

```
принят(x) ⇔ для каждой проверки c ∈ Требуемые(x):
              есть доказательство e: e.check = c, e.class = HARD, e.verdict = pass,
              e.subject_hash = H(x), проверка c доверенная (прошла свои контрольные случаи),
              и нет HARD-доказательства c с verdict fail или unknown на том же H(x)
```

Второе условие нужно потому, что проверки детерминированы и провал на том же хэше не перекрыть
проходом: статика Э1 в ядре и mypy в песочнице дают по доказательству на один хэш.

**Доверие.** Оболочка гоняет `selftest` при запуске и вносит доверенные проверки в
`Config.trusted`; `evaluate` ставит `trusted` по нему, нет поля — доверенных нет (map.md §12,
утверждено пользователем 29.09.2026).

| x | Требуемые(x) |
|---|---|
| разложение узла | П1, П2, П3, П4, П7 (П5 считается, но не требуется) + утверждение, если узел под утверждением |
| функция | Э1, Э2, Э3 |
| сборка составного узла | Э6(узел) + принятое разложение + все дети приняты |
| программа | Э6(корень) с примерами пользователя + I10 + все утверждения на текущих хэшах |

**Что это значит словами.**

* Принятая функция, разложение или сборка **соответствуют карточкам**, которые написали модели.
* Программа принята, когда ещё и **проходит примеры пользователя** на корне и на всех узлах, где
  пользователь их оставил. Только это и есть проверка против замысла.

SOFT-доказательства в правило не входят никогда.

## 11. Бюджет и воспроизводимость {#budget}

* **Бюджет** — токены и деньги на проект, фазу, роль и задачу; цены берутся из профилей
  операторов. Превышение → `PAUSED(бюджет)` и вопрос пользователю. Перед задачами К и Р размер
  подсказки считается заранее.
* **Воспроизводимость:**
  - каноническая запись JSON для хэшей;
  - зерно Z3, `derandomize` у Hypothesis, фиксированные тайм-ауты;
  - версии инструментов в каждом доказательстве;
  - **запрос каждой попытки — как он ушёл** (`ProviderRequest`: подсказка, схема, способ; ключей
    в нём нет), а не только хэш подсказки. Основания: CONTEXT_MODEL §7 — сохранять то, что
    реально ушло в модель, а не то, что предполагалось отправить; F45 — дефекты находились
    пересчётом по сырью; M1/M2 — вход шва не записывался, и вызовы, различающиеся входом,
    оказались неразличимы в логе и невосстановимы;
  - сырой ответ и `finish_reason` каждой попытки;
  - назначение оператора записывается до начала задачи — при той же карточке, тех же настройках и
    той же таблице решение то же.

  Ответы моделей недетерминированы, но **вердикт по данному ответу детерминирован** — этого и
  достаточно.
* **Журнал** — источник истины. Состояние любого элемента восстанавливается из журнала и
  доказательств. Незавершённая задача при возобновлении повторяется целиком.
